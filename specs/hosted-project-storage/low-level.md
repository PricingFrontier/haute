## Key types and data structures

- `StorageBinding` — frozen dataclass `{remote_url, branch, bound_by, bound_at}`, serialised as JSON. `branch` is the restart target — the working branch in effect at the most recent successful publication — written by `bind_remote` when it adopts an empty location and refreshed by `_record_restart_target` after every publish whose working branch differs from it; a populated bind records `None`. `from_payload` ignores unknown keys (a record written by a newer haute must not brick an older container) and raises `StorageUnavailableError` on a malformed or remote-URL-less record.
- `SyncStatus` — `{state: synced|pending|failed, pending: int, failure: transport|rejected|config|None, message: str|None}`. Counts and a failure CLASS plus hand-authored prose; never raw git stderr.
- `PushQueue` — one worker thread per process, guarded by a `threading.Condition`. State: `_pending` (unpublished commits), `_blocked` (do not attempt), `_terminal` (only a manual retry clears), `_failure`/`_message`.
- `_SessionState` — the one session singleton (`binding`, `lineage`, `queue`, `bind` task): one hosted container serves one project, and caching the binding and lineage keeps the frequently-polled readiness endpoint off the Files API. Tests reset the whole session with one assignment.
- `UCHead` — frozen dataclass `{generation, tip_sha, writer_id, bundle_name, written_at}`, one immutable `pointers/NNNNNN.json` record per committed generation under a `uc://` location, the highest of which is the head. `from_payload` tolerates unknown keys (same forward-compatibility rule as `StorageBinding`) and raises `StorageConfigError` (terminal) on a malformed record.
- `uc://` layout under `/Volumes/catalog/schema/volume/path`: `bundles/NNNNNN-<writer_id>.bundle` (generation-numbered AND writer-suffixed, each a complete `git bundle create --all`) plus `pointers/NNNNNN.json`, one immutable record per committed generation, created with a create-only upload after its bundle and naming the `bundle_name` it points at; the highest committed pointer is the head. Writer-unique filenames make bundle bytes immutable by construction — two racing writers can never overwrite each other's upload, only contend on one pointer path, which exactly one of them can create. `bundle_name` is required: a pointer without one is a corrupted record, not an older format (the format has no released version to be compatible with). `_UC_BUNDLE_RETAIN = 5` generations are kept (bundles and pointers pruned by the leading generation number, whatever the suffix). Alongside them: `CLAIM.json` (the lease) and, on forked locations, `LINEAGE.json` (provenance, written once at fork time, after the pointer — a crashed fork must not leave provenance for a project that never arrived).
- `UCClaim` — frozen dataclass `{app_name, writer_id, user, nonce, claimed_at, refreshed_at}`, the lease record. Lease constants: `_UC_CLAIM_HEARTBEAT_SECONDS = 30` (refresh cadence) and `_UC_CLAIM_STALE_SECONDS = 150` (5 missed beats → dead). A malformed claim record reads as stale, not as an error — a corrupt lease must not brick the location it guards.
- `UCLineage` — frozen dataclass `{parent_url, parent_generation, parent_tip_sha, forked_at, forked_by}`; `from_payload` tolerant like the others.
- `BindTask` / `BindStatus` — the background half of bind. `BindStatus` is `{state: idle|running|succeeded|failed, outcome: adopted|restart-required|None, message: str|None, claim: UCClaim|None, remote_url: str|None}`. One bind runs at a time; the status persists after completion so a UI that polls slowly still sees the result, and is cleared when the user acknowledges it.
- `_ClaimHeartbeat` — one daemon thread while a claim is held; each beat re-reads the claim, refreshes `refreshed_at` if it is still ours, and stops (without overwriting) if it is not — a stolen lease must never be re-stolen by a heartbeat.
- `_WriterState` — the one per-process writer singleton: the fencing identity (scope name + random suffix, minted lazily), the last-seen generation (set at restore and after each publish — the state behind supersession detection), and the held lease with its heartbeat. `hold_claim` is the single decision table every claim-taking path (bind, restore, publish) routes through, so the takeover/refusal rules cannot drift between callers.
- Errors: `StorageConfigError` (actionable misconfiguration → HTTP 400) and `StorageUnavailableError` (binding store unreadable → HTTP 503), both under `StorageError(HauteError)`; `StorageSupersededError(StorageError)` — another writer advanced the `uc://` pointer, classified as a terminal `rejected` sync failure; `StorageClaimedError(StorageError)` — the location is under another holder's live lease, carrying the structured holder record (→ HTTP 409 at bind, terminal `rejected` from the publish path).

## Control flow

**Boot** (`databricks_app/app.py` → `bootstrap.ensure_project`): refresh the vendored wheel → probe → `configure_git_credentials(~/.haute-runtime)` → `restore_if_bound(project_dir)`. `restored` clones the remote and rewrites `.haute/state.json` from the binding's branch; `present` reuses an existing clone; `unbound` seeds the standard scaffold plus a local repo. The process then `chdir`s into the project directory — before `haute.server` is imported, so pipeline discovery and the file watcher see the project, not the app bundle.

**Bind** (`POST /api/git/storage/bind`) is split at the fast/slow seam. The route runs only what is instant and local — URL validation, the already-bound refusal, and the state-volume requirement — so a typo is answered beside the input field. It then hands the rest to `BindTask` (one background thread, one bind at a time) and returns **202** with `outcome: "pending"`. The result reaches the UI through `storage_bind` on the readiness response: `running` while it works, then `succeeded` with the real outcome, or `failed` with a hand-authored message and, for a held `uc://` location, the holder record. A second bind while one is running is refused. `BindTask` lives on the `_SessionState` singleton, reset as one object in tests.

The background task validates the URL → `ensure_remote("origin", url)` → `remote_has_content`. Empty remote: `push_working_pair` first, then write the binding (a binding pointing at a remote we could not write to would promise durability the next boot cannot deliver), then activate the queue → `adopted`. Populated remote: write the binding and return `restart-required` WITHOUT activating the queue — the on-disk project is not that remote's project, so publishing from this process would push the wrong history. A `uc://` URL first acquires the claim (a live foreign holder → 409 with the holder record; the UI offers bind-elsewhere or fork), then branches on whether a committed pointer exists under the location; the adopt path publishes a first bundle generation instead of pushing.

**Save/commit → publish**: `commit_save` (via `_save_pipeline`) and `commit_milestone` (via the route) call `enqueue_push()` after success. That bumps a counter and returns; the worker calls `publish_bound_project`, which selects the transport from the active binding's URL scheme — `uc://` publishes a bundle generation, while other bindings use `push_working_pair`. N queued commits collapse into one publish either way. After the transport returns, `_record_restart_target` reads the clone's working branch and, when it differs from the active binding's, writes the refreshed record and caches it on `_session.binding`. A failed transport never reaches that step, and a `StorageUnavailableError` from the record write propagates as a `transport` failure, so the queue retries on the next save rather than reporting `synced` over a restart target the volume never received.

**Claim (`uc://`)**: `acquire_uc_claim` reads `CLAIM.json` → absent, stale (heartbeat older than `_UC_CLAIM_STALE_SECONDS`), malformed, or held by this app's own name → write our claim with a fresh nonce, read it back, and proceed only if the nonce is ours (the Files API has no compare-and-swap; write-then-verify shrinks the race to the read-back window, and the publish fence backstops what remains) → start the heartbeat. Held by another app within the lease → `StorageClaimedError` naming the holder. `release_uc_claim` deletes the record only if it is still ours (best-effort, called at clean shutdown via `atexit`).

**Publish (`uc://`)**: verify the claim — absent-on-a-claimless-location proceeds, ours proceeds and refreshes the lease, vanished-while-held is reasserted (a successor's shutdown may have deleted our live lease — see release), foreign-stale is taken over, foreign-live raises `StorageClaimedError` (a stolen lease must stop the old holder, not interleave with the new one) → read the head (the highest committed pointer) → early supersession check (see below; it only saves the packaging when the loss is already visible) → `bundle_create` locally (the only step under the repository mutation lock) → `bundle_verify` — the bundle is the only durable copy, so it is proven readable before it is trusted → upload as generation `head.generation + 1` under this writer's unique filename → **create `pointers/NNNNNN.json` for the new generation with a create-only upload** — this is the fence: the path already existing means another writer committed that generation in the window after our read, so nothing of theirs is touched, our orphaned bundle is deleted best-effort, and the publish stops as superseded; any other failure of the create is a retryable transport failure, and if the record did land regardless, the next attempt finds our own pointer as the head and simply publishes the following generation → record `{generation, tip_sha, writer_id}` in the clone's `.haute/uc-generation.json` (what the `present` restore path later verifies against) → prune generations beyond the newest `_UC_BUNDLE_RETAIN` (best-effort: a failed prune logs and never fails the publish).

The public function wraps that flow in one constant-space publish measurement.
`uc_publish_measurement` is emitted once per attempt, successful or failed, and
contains only `outcome`, nullable `generation`, `bundle_bytes`,
`lease_fence_ms`, `bundle_create_ms`, `bundle_verify_ms`, `upload_ms`,
`pointer_write_ms`, `local_record_ms`, `cleanup_ms`, derived `network_ms`,
and `total_ms`. `lease_fence_ms` includes the claim and the head read;
`pointer_write_ms` times the create-only pointer upload; `network_ms` is the
sum of lease/fence, bundle upload, and pointer-create phases; `cleanup_ms` is
best-effort pruning.
No URL, claim, writer, SHA, filename, exception text, or project content enters
the measurement. The existing `uc_project_published` success event retains its
generation and compressed byte count.

`tests/performance/test_external_scaling_perf.py` builds real Git histories at
10, 100, and 500 commits and publishes each complete repository through a
counting in-memory Files API. It records phase-separated measurements and
requires monotonic compressed size, one bundle upload plus one pointer upload
per publish, no more than five retained generations, a 500-commit bundle below
25 MiB, `bundle_create_ms < 5,000`, and `bundle_verify_ms < 2,000`. Fake upload
latency proves phase attribution but is not presented as a UC service latency.
Production `upload_ms` has a separate 30,000 ms p95 decision gate for bundles
within the size limit. Those bounds retain complete bundles; a bound failure
reopens the storage-format decision rather than silently installing incremental
state.

**Upstream check (`POST /api/git/storage/upstream/check`)**: read the bound location's `LINEAGE.json` (absent → not a fork, 400) → read the parent's head (its highest committed pointer; absent → the parent has nothing published, 400) → download the parent's pointed-at bundle to a temp file → `_git.fetch_bundle_refs(bundle, "upstream", cwd)` → measure both legs with `_git.pair_divergence("upstream", project_root, cwd)` → return the parent URL, the generation measured, both legs, and whether a fast-forward is possible (neither leg `ahead`/`diverged`/`unknown`, at least one `behind`).

Fetching from a bundle deliberately configures NO git remote: `git fetch <bundle-path> '+refs/heads/*:refs/remotes/upstream/*'` populates the tracking namespace and leaves `git remote` untouched. That matters because `_canonical_remote` picks from *configured* remotes, so `origin` remains the single divergence baseline (X5) and the milestone fork-gate cannot start comparing against the parent. The tracking refs persist after the temp bundle is deleted, which is all the display needs.

**Upstream catch-up (`POST /api/git/storage/upstream/pull`)**: re-run the check (the decision must be made on a fresh snapshot, exactly as `fast_forward_pair` re-fetches) → `_git.fast_forward_pair_from_tracking("upstream", project_root, cwd)` → the fork's working pair advances → `enqueue_push()` so the caught-up state is published to the fork's own location. Fast-forward only: a fork with its own commits is refused, naming both distances.

`fast_forward_pair` and the upstream path share one implementation. `fast_forward_pair` validates the configured remote and refreshes its tracking namespace with `_fetch_refs`, then calls `fast_forward_pair_from_tracking(namespace, project_root, cwd, *, source_label)`. The tracking helper verifies that both legs exist, refuses ahead or divergent histories, requires at least one behind leg, wipes volatile artefacts, applies `merge --ff-only` to the checked-out ledger, updates the working branch with compare-and-swap, and rolls both refs back on failure. The HEAD-on-ledger, dirty-tree, rollback, and cache-wipe rules therefore have one implementation for configured remotes and bundle-backed upstreams.

**Fork (`POST /api/git/storage/fork`)**: validate source and target URLs → the source must have a published generation, the target must have none (a fork never overwrites) → download the source's pointed-at bundle, verify it, upload it as the target's generation 1 → create the target's generation-1 pointer with a create-only upload (an existing pointer means the target was not empty after all, and the fork stops without overwriting it) → write `LINEAGE.json` after it (provenance is informational; a crash between the two loses only the fork label, never leaves a label for a project that did not arrive). The adopt path of bind additionally deletes any stale `LINEAGE.json` on its (empty) location, so an aborted fork's leftover label cannot attach itself to an unrelated project. The fork takes no claim — binding to the target later claims it — and copies only *published* state: the holder's unpublished work is theirs alone.

**Restore (`uc://`)**: `acquire_uc_claim` first (a boot cannot offer a dialog, so a live foreign claim gates with the holder named; the normal restart takes over its own app's claim immediately) → read the head (the highest committed pointer; absent → gate: the binding promises history) → download the pointed-at bundle → `git clone <bundle>` into the project directory → **verify the clone contains the pointer's `tip_sha`** (a mismatch means a torn multi-writer publish left the pointer describing bytes it does not own — gate loudly rather than restore the wrong project) → repoint `origin` to the `uc://` URL (a bundle clone leaves `origin` at a temporary file path, which would break the "is this clone the bound project?" check on the next boot) → write `.haute/uc-generation.json` → the shared tail (`adopt_cloned_lineage`, working-branch record, queue activation) proceeds exactly as for a git-remote restore. The `present` path claims the same way before reusing the clone.

**Failure gating**: a transport failure sets `_blocked` (cleared by the next save or a manual retry); a rejection or `GitDomainError` also sets `_terminal` (only a manual retry clears it), so a diverged remote is not hammered by every subsequent save.

## Edge cases and invariants

- An unreadable, corrupt, or non-object binding record raises rather than reading as "unbound" — the invariant that stops a fresh project being seeded over durable work.
- `remote_has_content` propagates errors: an unreachable remote must never read as "empty" and trigger an adopt that publishes over someone else's project.
- Remote URLs are restricted to `https://`, `file://`, and `uc://`; embedded credentials are refused (they would land in `.git/config` and every remote-tracking log line). Plain `http://` and `ssh://` are rejected.
- A `uc://` URL must name a three-part volume (`catalog.schema.volume`) plus a non-empty project path with no empty, `.` or `..` segments — the path is joined under `/Volumes/` for the Files API, so a traversal segment would escape the volume.
- Supersession rule: publishing is refused (terminally, as a `rejected` failure) when the pointer was written by a different `writer_id` at a generation other than the one this process last saw. The generation this process restored from is exempt — that pointer was legitimately written by the predecessor container whose lineage this one adopted. That check runs before packaging and is an optimisation; the create-only pointer write is what makes the rule hold under every interleaving: a competitor committing the same generation after our read is refused at the create, never overwritten.
- The `present` restore path (an existing clone survived a process restart) arms the same fence: the new process blesses the current generation only when the volume's pointer exactly matches the clone's own `.haute/uc-generation.json` record (generation, tip, and writer) — mere presence of the tip commit in the clone is NOT identity, since another writer can legitimately publish a commit this clone also happens to contain. No record, or any mismatch, leaves the fence armed and the first publish stops as superseded instead of overwriting the newer generation.
- The own-app claim takeover applies only when `DATABRICKS_APP_NAME` is actually set: every process without it shares the fallback scope `local`, and two local dev processes must arbitrate by lease expiry like strangers, not seize each other's claim on sight.
- `release_uc_claim` deletes only a record still carrying our nonce, but no compare-and-swap exists, so a successor's fresh lease can still be deleted in the read-to-delete window. Both the heartbeat and the publish-time verification therefore treat "our claim vanished while held" as *reassert*, not *lost* — the successor heals within one beat, and the writers still resolve loudly at the pointer fence.
- The claim is advisory steering, the fence is correctness: every hazardous interleaving the claim fails to prevent (write-then-verify race window, lease stolen during a stall, a competitor landing after our head read) still terminates in a loud stop at the pointer create, never a silent overwrite — provided the volume honours create-only uploads atomically, which `scripts/uc_create_only_qualification.py` verifies against an isolated volume path (see Testing).
- A heartbeat that finds a foreign claim stops beating and never overwrites — re-stealing a stolen lease from a background thread would turn one loud stop into a silent tug-of-war.
- Clock skew: staleness compares volume-record timestamps across containers; `_UC_CLAIM_STALE_SECONDS` (150 s) is far above plausible NTP skew on the platform, and the own-app takeover shortcut makes the common restart path skew-independent.
- Claims and lineage are per-location metadata, invisible to git: they never appear in a working tree, travel in no bundle, and sit outside `bundles/` so retention never touches them.
- The upstream check is on-demand only, never on the polled readiness path: it downloads a whole bundle, and readiness is polled continuously by every open tab.
- A fork is a complete project, not a dependent one. An unreadable, emptied, or deleted parent fails only the check — never the fork's own save, publish, or boot.
- Upstream catch-up is one-directional by design (parent → fork). Publishing a fork's work back to its parent would mean writing to a location another app holds the claim on, which the claim layer exists to prevent; that direction needs its own design.
- Pointer-written-last is also the read-side contract: a bundle uploaded without its pointer (a torn publish, or a create that lost the race) is invisible to restore, which only ever follows the highest committed pointer; the orphan is removed by a later prune.
- The askpass helper contains no secret: it reads `HAUTE_GIT_TOKEN` from the environment at call time, is written `0700`, and answers the username prompt separately from the password prompt.
- `enqueue` on a queue that was never started (every local session) is inert, so the save path is unchanged off the hosted platform.
- `storage_state()` returns `unsupported` without `HAUTE_STATE_VOLUME`, which hides the whole surface in the UI rather than offering an action that cannot work.
- The worker never holds the queue lock across a push, so it cannot deadlock against the repository mutation lock `push_working_pair` acquires.
- The restart target moves only with a successful publish: `bind_remote` and `_record_restart_target` are the binding record's only writers, both after the transport succeeded. A branch selected, forked, archived or deleted without a later publish is clone-local and moves nothing durable (branch removal has no remote side effects, so the stored project keeps the branch the target names). A target the stored project lacks can therefore only come from a record older than the stored history; that boot logs `restored_branch_missing`, serves the project with no working branch, and lets the user choose one.

## Error handling

`StorageConfigError` → 400 with the setting named; `StorageUnavailableError` → 503; a malformed or unparseable pointer record raises `StorageConfigError` (terminal — a corrupted pointer cannot be published past by retrying, so the sync chip must not promise "will publish on the next save"); `GitPushRejectedError` → 409 with the structured rejection; other `GitError` → the existing `_handle_git_error` sanitiser. `_with_storage_state` never raises: storage is additive to git readiness, and a storage fault must not blank the branch indicator — it surfaces through the sync state instead. Clone and push failures log stderr server-side and return hand-authored prose, per the MAGINOT low-context-error class.

a pointer create that fails before commit is retried; an ambiguous create that did land is reconciled on the next attempt; a scripted two-writer history has every acknowledged generation strictly ordered and never replaced; and a fork never overwrites a target pointer. `tests/test_storage_routes.py` covers the HTTP surface and pins that no absolute path or raw stderr reaches the response body. Frontend behaviour is covered in `frontend/src/components/__tests__/BranchIndicator.test.tsx` and `frontend/src/types/__tests__/guards.contract.test.ts`.

Known gaps: no test exercises a real HTTPS remote or a real UC volume (the live smokes in `databricks_app/LEARNINGS.md` cover those paths manually). The publication guarantee is conditional on the Files API honouring `overwrite=false` atomically under concurrent creates, which no offline test can prove: `scripts/uc_create_only_qualification.py` runs that qualification against an isolated volume path (several rounds of simultaneous create-only uploads must each admit exactly one writer, whose bytes are what the object then holds), and its result is to be recorded in `databricks_app/LEARNINGS.md` before the guarantee is claimed for production.

## Storage scope boundaries

The component supports one app session, one project, one storage location, `uc://` bundle persistence, lease-based claims, storage forks, upstream visibility, and fast-forward-only catch-up. Clean shutdown releases a held claim best-effort; unclean shutdown relies on lease expiry and the own-app takeover rule.

The following behaviours are explicitly unsupported rather than partial implementations:

- **Merging divergent history.** When both fork and parent have moved, catch-up is refused. A text merge is unsuitable for generated pipeline files, and no node-level merge contract exists in this component.
- **Publishing a fork's work back to its parent.** The claim layer prevents writes to a parent location held by another app; this component provides parent-to-fork catch-up only.
- **Live rebinding or save-as-copy.** A populated target produces `restart-required`; the running process never publishes its current project into that target.
- **Per-commit authorship from the forwarded user identity.** `bound_by` records who bound the project and request logs carry the per-request user, but commits are authored by the app identity.
- **A per-browser-session claim on the app itself.** Two tabs of one app are one writer to storage, so the volume claim cannot arbitrate them.
