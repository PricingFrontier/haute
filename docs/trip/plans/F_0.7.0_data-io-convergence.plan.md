# Data I/O Node Convergence Implementation Plan

Target version: **0.7.0** (provisional minor release, after the 0.6.0 Polars
backend remediation). This is a deliberate pre-1.0 hard cutover: two duplicate
node types are removed, `dataInput` and `dataOutput` gain their retained
functionality, the input cache becomes provider-neutral, and the data-I/O wire
contracts change.

Ruling, 2026-07-24:

- `dataInput` is the only authored tabular source node and may appear multiple
  times in a pipeline;
- `dataOutput` is the only authored tabular persistence node and may appear
  multiple times;
- `dataSource` and `dataSink` have no backward-compatibility path;
- repository-owned pipeline/model graphs containing either removed node start
  again as blank pipelines rather than being converted;
- Data Input retains the optional Polars editor; Data Output does not gain one.

## Outcome

Deliver one coherent data boundary:

`provider/group → format/connection → direct or snapshot read → optional input Polars code`

and one coherent persistence boundary:

`upstream lazy plan → destination group/format → explicit Write → staged/transactional publication`

The user chooses File, Database, Lakehouse, Databricks, or Inline in one Data
Input editor. Registry-backed groups expose only supported formats and modes.
Databricks keeps its browse/fetch experience while using the same source-
snapshot store as database and lakehouse inputs. Direct and cached execution
advertise separate bounded/chunk capabilities. Data Output mirrors the grouping
and format language, filtered by real writer capabilities, and retains the old
Data Sink editor's explicit Write action and atomic file publication.

This is not a second execution engine, a second format list, or a generic object
cache. `haute.projection`/`haute.execution` remain the planning boundary, the
Polars/provider registry is the one capability authority, and the source-
snapshot cache is a single-table external-boundary cache distinct from API-input
JSON shredding and graph dataframe caching.

if evidence changes the design, amend and re-review the spec before code. At
release, fold each approved contract into the ordinary present-tense sections
and remove the temporary section.

## Scope and non-goals

In scope:

- one backend/frontend capability registry for provider groups and per-direction
  format legs;
- strict `DataInputConfig`/`DataOutputConfig` discriminated validation;
- direct and snapshot input execution;
- shared snapshot lifecycle for cache-capable files, databases, lakehouses, and
  Databricks;
- capability-driven chunk sources beyond CSV/Parquet where proven;
- optional post-read Polars code on Data Input;
- grouped Data Input/Data Output editors and explicit output Write;
- atomic local-file output and declared transactional/non-transactional remote
  publication;
- removal of all legacy enum/decorator/config/editor/runtime/test paths;
- reset of repository-owned affected pipeline/model assets to blank; and
- deploy, trace, optimiser, assistant, scaffold, docs, and release convergence.

Out of scope:

- a Databricks output writer;
- pretending every readable format is writable or directly chunkable;
- remote object-store credential support without a separately approved secret
  and transport contract;
- implicit cache build/refresh during graph execution, deploy, preview, or
  generated-module import;
- calling an eager cache build “bounded” because its result is Parquet;
- per-chunk execution of whole-frame Polars operations;
- output-local Polars code;
- migration/alias/deprecation support for removed nodes;
- salvaging removed configs or topology from repository model pipelines; and
- changing `apiInput` live-request or `output` JSON-response semantics.

## Compatibility and reset policy

There is intentionally no backward compatibility:

- delete `NodeType.DATA_SOURCE`, `NodeType.DATA_SINK`, `data_source`,
  `data_sink`, `DataSourceConfig`, `DataSinkConfig`, their sidecar folders,
  builders, codegen templates, editors, routes, catalogue entries, and tests;
- parser/config/codegen do not recognise or translate the removed tokens;
- do not add warnings, aliases, migration commands, hidden load repair, or
  “legacy” branches;
- reset checked-in authored/model/example pipeline graphs which contain removed
  nodes to the repository's standard blank-pipeline form, deleting their
  orphaned I/O sidecars; and
- tests needing an I/O graph construct a new retained-node fixture explicitly.

The 0.7.0 release note states that old pipelines must be recreated from a blank
pipeline. It does not advertise a converter that does not exist.

## Delivery protocol

The root agent owns architecture, config/wire shapes, test design, boundedness
decisions, security, cache identity, integration review, and completion. Use
workers only for bounded inventories, deterministic fixture rewrites after the
root defines the transformation, predefined command batches, or narrowly
specified implementation. No worker decides whether a format is bounded,
transactional, secure, or semantically equivalent.

Every numbered package follows red-green-refactor:

1. Re-read the approved contract and define the smallest failing tests.
2. Prove the pre-change failure is the intended one.
3. Implement the smallest coherent slice without compatibility fallbacks.
4. Run the targeted test, affected module, touched-file lint/format/type checks,
   and cross-stack contract tests where relevant.
5. Inspect the actual diff and reconcile implementation evidence with the spec.
6. Keep at most one phase package in an intentionally failing cross-stack state;
   do not leave the repository broadly red between phases.

Performance evidence should prefer structural measures—batch sizes, maximum
resident batches, scans, collections, cache generations, and scaling
ratios—over noisy wall-clock thresholds.
