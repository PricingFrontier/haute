# Polars Backend Remediation Implementation Plan

Target version: **0.6.0** (provisional minor release, after the input-identity
0.5.0 work). The release is minor because it introduces a versioned execution-
strategy diagnostic contract and deliberately changes several silent fallbacks
into named errors.

Haute is still pre-1.0, so this is an intentional compatibility-changing minor
release. The release notes and migration guide must call out each former silent
fallback that now returns HTTP 422, plus removal of any audited private fallback
helper. Unsafe compatibility shims are not allowed.

Sources:

- the retired point-in-time Polars backend review from 2026-07-06, whose
  dispositions are preserved in this plan;
- the approved execution-engine and related component specifications;
- `docs/roadmap/backend-execution-hardening.md` (shared metrics, fault and
  performance-harness ownership); and
- the approved change contracts in `docs/specs/` linked below.

## Outcome

Make Haute's Polars-backed execution stack faster on its proven hot paths,
fail-loud at correctness boundaries, consistent across every execution surface,
and observable enough that a user can understand projection, boundary and
rejection decisions without reading server logs.

This is not a new engine or a second planner. `haute.projection` remains the
single planning implementation and `haute.execution` becomes the sole
application-facing planning boundary. Existing bounded collect, sink,
checkpoint, dataframe-cache and chunk-runner contracts remain load-bearing.
Nothing classified as cleared by the source review is in scope.

## Spec-first contract

Planning starts by updating the owning specifications, before failing tests or
production code. `docs/specs/README.md` and `docs/specs/TEMPLATE.md` define the
temporary `## Approved change contract` form: it records agreed future
behaviour without falsely presenting it as shipped. The implementation/release
change for each batch must fold that contract into the ordinary present-tense
spec sections and remove the temporary section.

Approved contracts for this programme live in:

- `docs/specs/execution-engine/` — planning, eager/lazy/chunk execution,
  memory and admission;
- `docs/specs/caching/` — preview identity, cache-store outcomes and input
  fingerprints;
- `docs/specs/tracing/` — correlation, representation and cache reuse;
- `docs/specs/json-shredding/` — OUTPUT assembly and JSON-cache validity;
- `docs/specs/rating/` — rating lookup and combine semantics;
- `docs/specs/io-layer/` — streaming classification and source counters;
- `docs/specs/mlflow-model-registry/` — empty-batch and projected scoring;
- `docs/specs/pipeline-config/` — live-switch and node-arity contracts;
- `docs/specs/modelling/`, `optimiser/` and `deploy/` — planner-consumer and

- `docs/specs/engineering-quality/` — deterministic scale scenarios and the

No implementation batch may start until its exact approved contract has been
reviewed. If implementation evidence changes the design, amend and re-review
the spec first; do not let code silently redefine the contract.

## Delivery and delegation protocol

The root agent owns every numbered implementation batch end to end. It
interprets the approved contract, chooses architecture and APIs, designs the
test strategy and edge cases, resolves implementation surprises, reviews the
actual diff, integrates the result, runs final verification and decides whether
the batch is complete. Worker output is provisional evidence, never a substitute
for root inspection or judgment. Silent-wrongness and public-contract decisions
remain in the root thread.

Workers are optional bounded execution help, not mandatory package roles. Use
the fewest that materially reduce wall-clock time: normally none or one, and
never more than two concurrent subagents. Concurrent tasks must be independent,
must not edit the same files and must not duplicate work. Workers receive a
self-contained prompt with exact scope, inputs, constraints, expected output
and verification command, and they must not spawn further agents. Do not create
developer/reviewer pairs or delegate planning, architecture, test design,
ambiguous implementation, review, integration or final synthesis.

Use the custom `luna_worker` without a model override for genuinely batched,
repeatable grunt work: source/test inventories, fixture or parameter-matrix
expansion after the root defines the cases, benchmark/log capture,
documentation link checks, deterministic transformations and repetitive
frontend fixture updates. Candidate batches are P1/P10 consumer inventories;
P2-P4 fixture expansion and structural counters; P5's Polars-error corpus;
P6-P8 benchmark/call-count capture; P9a's predefined dtype/golden cases;
P9b/P11 key-mutation fixtures; P12/P13 schema and frontend fixture regeneration;
P14 deterministic data/report generation; and P15 export/call-site inventories.
The root reviews every generated artifact and decides every threshold, error
contract and implementation design.

Use an explicitly configured `gpt-5.6-terra` worker at low reasoning only for a
narrow test or code implementation after the root has supplied the design,
test cases and acceptance criteria. Medium reasoning is reserved for a tightly
specified implementation that demonstrably needs it. Use `fork_turns: "none"`
or the smallest essential recent-turn slice, never full-history inheritance.
If a task cannot be specified that tightly, keep it in the root thread. Worker
assignments are selected when a batch begins; this plan does not pre-allocate a
worker to every package.

For every batch:

1. The root re-reads and, if necessary, refines the approved change contract.
2. The root defines the smallest non-overlapping failing tests and relevant
   boundaries, invalid inputs, state transitions, concurrency cases and past
   regressions. A worker may only implement a test matrix after those cases are
   specified.
3. Confirm the tests fail for the intended reason on the pre-change code.
4. The root implements the change directly or delegates a tightly specified
   implementation remainder to Terra. Build the smallest coherent design that
   satisfies the contract and do not add broad fallbacks.
5. Run the targeted red-green-refactor loop, then the affected format, lint,
   type, contract and integration checks. Climb to quick/full preflight only
   when the batch or phase risk warrants it.
6. The root inspects the actual diff and evidence for spec/code/test agreement,
   regressions, maintainability, user experience, performance and absence of
   changes to cleared behaviours.
7. Reconcile the approved contract into the ordinary spec text and remove its
   temporary section in the same implementation batch.

Performance assertions should normally count scans, hashes, collections,
Polars cache ids or scaling ratios. Do not add wall-clock CI thresholds unless
the existing performance harness has first established a stable noise envelope.

## Phase 0 — Approve the specification deltas

This planning phase changes specifications only; it does not change production
code or tests.

- Add and review the approved change contracts listed above.
- Choose the projection-based roadmap design: retain `ProjectionPlan` as the
  internal planning representation, but define a stable, closed strategy
  vocabulary and versioned JSON-safe diagnostics at the execution facade.
- Decide group-by V1 explicitly: no partial/final reducer catalogue in 0.6.0.
  A group-by never enters the chunk runner. It is either a declared full
  `materialisation-boundary` under a profile that permits full materialisation
  after RAM admission succeeds, or it raises
  `GroupByExecutionUnsupportedError` before execution. It is not represented as
  an unprojected-streaming boundary or ordinary bounded execution.
- Record explicit unavailable states for metrics and estimates. Zero means an
  observed zero; it must never mean unsupported or unmeasured.
- Approve the V1 public errors and route mapping:
  `GroupByExecutionUnsupportedError(BoundedMemoryUnsupportedError)`,
  `RatingExtremaUndefinedError(ExecutionError)`,
  `RatingFactorMissingError(SchemaMismatchError)`,
  `LiveSwitchScenarioError(ExecutionError)` and
  `OutputNestingKeyError(OutputMappingSchemaError)`, plus
  `TraceCorrelationUnsupportedError(ExecutionError)`, all map to HTTP 422 and to
  `contract_error` in background jobs, with stable codes and named fields.
- Record compatibility decisions: additive fields retain `schema_version=1`
  and are ignored by V1 readers; malformed payloads, unknown V1 enum values and
  unsupported higher schema versions become an explicit diagnostics-
  unavailable state. Silent live-switch fallback and the identified silent-
  wrongness cases deliberately become loud failures.

**Done when:** each owning spec states target behaviour, non-goals, failure
semantics and acceptance evidence, and the plan/spec links are valid.

## Phase 1 — Planner foundation and independent correctness packages

### P1. Canonical strategy contract and group-by boundary

**Resolves:** execution-strategy roadmap sections 1 and the immediate decision
part of 4.

Keep one planner. Define `schema_version=1` and the closed internal vocabulary
`projected`, `schema-all-except`, `full-width-admitted-eager`,
`unprojected-streaming-boundary`, `materialisation-boundary`, `unsupported` and
`not-planned`. Map it to the public status exactly as follows:

| Internal strategy | Public status |
|---|---|
| `projected`, `schema-all-except` | `projected` |
| `full-width-admitted-eager` | `admitted_eager` |
| `unprojected-streaming-boundary`, `materialisation-boundary` | `boundary` |
| `unsupported` | `rejected` |
| `not-planned` | `not_planned` |

Every V1 DTO requires `schema_version`, `status`, `strategy`, `profile`,
`boundedness`, `reason_code` and `detail_state`. Boundary/reason collections are
capped at 32 items, provenance at 128 items, and human message/remediation fields
at 512 characters, with deterministic truncation. A caller-supplied seed at an
opaque multi-consumer node must either be preserved safely or return a reason
explaining why it cannot apply; it must not be indistinguishable from an
unseeded result. Only deliberately supported facade and diagnostic types remain
public.

Each bounded collection is `{state, total_count, items}`. `available` requires
`total_count == len(items)`; `truncated` requires `total_count > len(items)`;
`unavailable` requires `total_count=null` and no items. Producers canonical-sort
before slicing. Boundaries sort by `(topological_rank, node_id, operator,
boundary_kind)`, where rank comes from a canonical topological sort with lexical
node-id tie breaks. Reasons sort by `(topological_rank-or-max, node_id-or-empty,
reason_code, operator-or-empty)`. Provenance sorts by `(column, origin_kind,
source_node_id-or-empty, source_column-or-empty)`. All compare Unicode code
points ascending. After those primary tuples, the producer uses the server's
canonical JSON serialisation as an internal final tie-break so truncation is
deterministic; exact duplicates remain. That internal tie-break is not part of
the wire-order contract: consumers validate only nondecreasing primary tuples
and accept any order within an equal-primary group. The top-level `detail_state`
is the worst child state in the order
`truncated`, `unavailable`, `available`. An over-cap or internally inconsistent
consumer payload is malformed and becomes diagnostics unavailable; clients do
not silently truncate it.

Group-by code remains excluded from chunk-local execution. Planner results must
return a declared full-materialisation boundary only when the selected profile
allows that boundary and RAM admission succeeds. Every other case raises
`GroupByExecutionUnsupportedError(BoundedMemoryUnsupportedError)` before data
execution, names node/operator/profile/remediation, and maps to HTTP 422.
`BoundedChunkReducer` is not group-by support.

The profile policy is closed in V1:

| `ExecutionProfile` | Group-by outcome |
|---|---|
| `PREVIEW_EAGER`, `DEPLOY_LIVE` | `materialisation-boundary` only with an available P4 estimate and admitted context whose effective headroom covers it; otherwise typed rejection |
| `LAZY_SINK`, `TRAINING_PREP`, `OPTIMISER_SETUP`, `EXPLORE_ANALYSIS`, `AUTO_RANGE`, `DEPLOY_BATCH`, `CHUNKED_MAP_REDUCE` | Always `GroupByExecutionUnsupportedError`; these profiles require bounded execution |

Effective headroom is
`min(admission.memory_limit_bytes, admission.headroom_bytes)`, with both values
present and positive. The estimate must have explicit `available` state and
`estimated_peak_bytes <= effective_headroom`; zero bytes is a valid empty-input
estimate, never the encoding for unknown. Rejection reason codes are exactly
`execution_admission_unavailable`, `materialisation_estimate_unavailable`,
`materialisation_exceeds_headroom`, or `profile_requires_bounded_execution`.
Precedence is profile rejection first; then missing/invalid admission; then
unavailable estimate; then over-headroom; otherwise admit the boundary.
The error fields are `node_id`, `operator`, `profile`, `reason_code`,
`remediation`, nullable `estimated_peak_bytes`, and nullable `headroom_bytes`.

**Tests first:** table-driven graph × profile × seed × reason cases, including
every profile and missing/unknown/empty/equal-to-headroom/over-headroom admission;
prepared
versus request-plan conformance; strict/non-strict opaque fan-out; diagnostics
schema version and deterministic truncation; exported-name/API hygiene; every
group-by shape stays off the chunk runner.

**Primary files:** `src/haute/projection.py`, `src/haute/execution.py`,
`src/haute/chunking.py`, `src/haute/_execution_context.py`, `src/haute/schemas.py`.

**Done when:** one route-facing planning contract returns an explicit result for
every invocation and every group-by has an honest admitted/boundary/rejected
outcome.

### P9a. Trace correlation correctness and responsiveness

**Resolves:** Review-P03 / FR-03 through FR-11. FR-06's loud duplicate rejection is
already implemented; this batch preserves it while vectorising relocation.

Implement in semantic order: one dtype-aware tolerance expression shared by
all matching paths; vectorised uniqueness/exact/relaxed matching; remove the
duplicated shared-column fast path; vectorise target relocation while retaining
409 ambiguity; route every value through the canonical preview JSON-safe
representation; attach an explicit low-confidence diagnostic when a narrow
relaxed subset wins; and introduce request-scoped enrichment memoisation.

The V1 matcher uses vectorised native comparisons for null, booleans, integers,
floats (shared tolerance with explicit NaN/Inf rules), strings/binary, temporal/
duration, decimal, categorical/enum normalised to string, and same-schema list/
array/struct values through Polars 1.39.3 native equality against a typed one-row
literal. Object or incompatible
nested keys return `unsupported_dtype`; they never trigger a Python full-frame
fallback. Target relocation raises
`TraceCorrelationUnsupportedError(ExecutionError)` (`trace_correlation_unsupported`,
HTTP 422/background `contract_error`, fields `node_id`, `key_columns`, `dtypes`,
`reason_code`); its two arrays remain positionally aligned in deterministic
correlation-key order and are truncated together to the first 16 pairs. Parent resolution
remains unresolved with a typed diagnostic.

Finite floats match exactly when
`abs(a-b) <= max(1e-12, 1e-9 * max(abs(a), abs(b)))`. Booleans are not numeric;
integers match integers exactly; int/float uses the formula only when the integer
is within ±2^53 and the float is finite; unsafe integers match only their canonical
decimal string. NaN matches only NaN/the `nan` sentinel, positive infinity only
positive infinity/`inf`, and negative infinity only negative infinity/`-inf`.
Date matches Date by day; Time by nanosecond-of-day; Datetime is losslessly
normalised to integer UTC nanoseconds with aware-to-aware and naive-to-naive only;
Duration is checked signed integer nanoseconds. Cross-family or lossy temporal
conversion is unsupported. Decimal comparison losslessly rescales integer
coefficients to the maximum scale and never uses float; precision overflow is
unsupported.

The result fields are `candidate_count: int|null`, `candidate_indices: list[int]`
and `candidate_indices_state: available|truncated|unavailable`. Supported matches
report the exact count and the first 16 original physical row indices in ascending
order (`available` through 16, `truncated` above 16). Unsupported comparison has
null count, no indices and `unavailable`.

Use a completed-result memo separate from a per-call-path active recursion stack.
The memo key contains node, concern, column, canonical row identity, frame/port
and every concern input. Push/pop the active stack per recursion path; a cycle
produces the existing structured cycle/error marker without suppressing sibling
diamond work. Only completed successes are memoised and nothing survives one
`execute_trace()` request.

**Tests first:** both correlation paths over the same float boundary; exact and
duplicate rows; reorder-capable and order-preserving transforms; null/NaN/Inf,
unsafe integers, dates/datetimes/decimals/list/struct values; object and
incompatible-nested rejection; exact numeric/non-finite/temporal/decimal boundary
tables; candidate counts at 0/1/16/17 with ordering/state; public unsupported
error parity; zero Python
full-frame iteration on vectorisable paths; relaxed width/confidence; enrichment
diamonds, cycles, repeated references and non-memoised failures; golden/API
response parity; structural scaling tests in the existing
performance lane.

**Primary files:** `src/haute/_trace_correlation.py`, `src/haute/trace.py`,
`src/haute/_trace_enrichment.py`.

**Done when:** trace row identity is consistent across paths, ambiguity remains
visible, values match preview representation, and warm correlation has no
avoidable Python full-frame scan.

### P11. Lineage-scoped preview cache identity

**Resolves:** Review-P05 / FR-15. Depends on P5's explicit cache-store outcome and the
stable P1/P10 planning contract.

Introduce one shared cache-key factory over the original graph and the source-
pruned result of `prepare_graph(graph, target, source)`. Its mandatory,
normalised fields are target, source/`active_source`, requested columns, initial
width, row limit, port/frame handle, contract fingerprint, selected live-switch
path, relevant runtime/input fingerprint and execution-semantics version. The
canonical lineage payload uses deterministic ordered relevant nodes/edges and
preserves graph-level `preamble`, `source_file`, `preserved_blocks`, `sources`
and `active_source`; downstream and disconnected state is excluded.

Cache-store eligibility is checked before mutation. An oversized same-key store
retains the old entry, evicts nothing and cannot be pinned. An accepted store is
atomic under the cache lock; readers observe a complete old or new value, the
last completed accepted same-key store wins, and byte/entry accounting remains
coherent. Only a retained store may acquire a request lease/pin and all leases
release in `finally`; unexpected store failures propagate.

**Tests first:** a downstream-only edit preserves an upstream target hit; mutate
each mandatory field and each graph-level identity field independently; unrelated
