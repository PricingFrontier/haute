### 1. Generated liveSwitch body hard-wires the 'live' input; standalone pipeline.run() (source=batch) diverges from canvas executor branch selection

- **Subsystem:** codegen | **Category:** semantic-equivalence | **Severity:** high | **Effort:** M | **Confidence:** high | **Method:** executed-repro
- **Location:** `src/haute/_codegen_builders.py:521-539 (_gen_live_switch); src/haute/pipeline.py:327-362 (Pipeline.run sets _scenario_ctx='batch' and calls the literal body via Node.__call__ at pipeline.py:54-68); src/haute/_builders.py:633-666 (_build_live_switch routes by ctx.source)`
- **Failure:** A liveSwitch node maps input 'live_src'->scenario 'live' and 'batch_src'->scenario 'batch'. - **Evidence:** Three code paths confirmed both by trace and by execution. (1) Codegen: src/haute/_codegen_builders.py:268-273 `_LIVE_SWITCH` template body is `return {active_param}`, and :521-539 `_gen_live_switch` sets active_param = the input whose input_scenario_map value == 'live' (a SAVE-time constant). ### 4. shred_to_buffers silently flattens a nested list inside a scalar array, emitting MORE rows than source elements with zero skip accounting

- **Subsystem:** cache | **Category:** silent-failure | **Severity:** high | **Effort:** S | **Confidence:** high | **Method:** executed-repro
- **Location:** `src/haute/_json_shred.py:597-618 (the `_walk` list branch recurses into list elements unconditionally) interacting with the scalar-table emit at 628-639`
- **Failure:** The region's central invariant is zero silent record loss / conservation: every array element at an emitting table's depth is either emitted as exactly one row or counted in ShredSkipStats. For a scalar child table ($value column) whose source array contains a nested list element (e.g. tags: ['a', ['b','c'], 'd']), _walk iterates the outer list, hits the inner list element, and recurses — iterating the inner list AGAIN — so 3 source elements produce 4 emitted rows, with skipped == {records:0, rows_by_table:{}}. The cached parquet's row count silently exceeds the source element count, and the extra 'c' row has no provenance. validate_v2_schema does not reject this (it validates schema shape, not data), and build_per_port_cache shreds the user's/externally-supplied config directly, so unlike inference there is no nested-array guard. Verified: emitted rows [a,b,c,d] (4) from a 3-element array, skip stats empty.
- **Evidence:** Ran the repro: shred_to_buffers([{"tags": ["a", ["b","c"], "d"]}], scalar_$value_cfg, stats=ShredSkipStats()) emitted 4 rows with $value column ['a','b','c','d'] from a 3-element source array; stats.total == 0 and as_meta() == {'records': 0, 'rows_by_table': {}}. Conservation (emitted + skipped == element_count) FALSE: 4 + 0 != 3. Contrast case in the same run confirmed the mechanism exists: an object-array scalar intruder [{...},"intruder",{...}] is correctly counted as skipped_rows_by_table == {'drivers': 1}, 2 rows emitted.

Root cause src/haute/_json_shred.py:597-618: the _walk list branch does `for item in value: ... _walk(item, current_path)` (line 617) with NO shape check. A list element re-enters the list branch (line 600) and iterates the inner list, emitting one scalar row per inner element. It never reaches the shape-mismatch skip at lines 628-632 where, for an object array, `is_scalar_table != (not is_dict)` would trigger _count_row_skip. _resolve_leaf line 523 would have resolved a list under $value to None (one row) had it reached the emit path — but the list branch swallows it first into multiple rows.

Inference guard does NOT cover this path: infer_v2_schema_from_data raises ApiInputSchemaError for array-of-arrays at _json_shred.py:1171-1177, but build_per_port_cache (line 776/826) only calls validate_v2_schema (shape-only, never inspects data records — confirmed reading _api_input_schema.py:263-364) then shreds the on-disk/externally-supplied config directly. json_cache.py:384 feeds the persisted config. If the data file gains a nested-list record after inference, or a nested-list record falls outside the inference sample-size cap, the guard never fires.

Genuinely unpinned: the scalar-child conservation property test tests/test_json_shred_properties.py:72-107 has the correct assertion (len(buffers['tags']) == sum(len(r['tags']) for r)) but draws tags elements from st.one_of(st.text(max_size=5), st.none()) at line 77 — nested lists excluded, so it never exercises this case. test_nested_scalar_array_fails_loud (test_scalar_array_and_inference.py:317) only covers the inference path.
- **Fix:** In the _walk list branch (src/haute/_json_shred.py:600-618), do not recurse unconditionally into list elements. Mirror the null-element handling already present: when an element is itself a list (isinstance(item, list)) it is a shape mismatch for every table at current_path — for a scalar table count it via _count_row_skip(label) (one skipped row, preserving conservation), and for an object table likewise count it (an array-of-arrays element is not a record). I.e. only `_walk(item, current_path)` when item is a dict (descend) or recurse for the legitimate scalar case; a list element must be counted, never flattened. Add a property/regression test: extend the scalar-child strategy at tests/test_json_shred_properties.py:77 to include nested lists in the element space (or add a focused test asserting emitted + skipped == total for {"tags": ["a", ["b","c"], "d"]}), so the conservation law is pinned for the list-element case. Optionally add a defensive build-time data check, but the shred-level skip-count is the minimal correct fix.
- **Repro:** `cache__shred-nested-list-scalar-array-row-inflation.py` - PASS (exit 0): BUG REPRODUCED. [case1] emitted rows = 4 from 3 source elements; emitted $value = ['a','b','c','d']; skip stats total = 0; conservation holds? = False. ### 5. Byte-budget chunk sizing estimates target row width from SOURCE schema only, so downstream-created wide/string columns fall back to 64 bytes and the target chunk can exceed the memory budget

- **Subsystem:** execution | **Category:** resource-leak | **Severity:** high | **Effort:** M | **Confidence:** high | **Method:** executed-repro
- **Location:** `src/haute/chunking.py:607-626 (_plan_chunk_sizes target_row_bytes), 629-651 (_estimate_projected_row_bytes), 654-692 (_source_projected_column_widths)`
- **Failure:** A byte-budget chunk plan (target_chunk_bytes set, chunk_size=None) over a graph whose chunk suffix CREATES columns the source does not have: e.g. dataSource(parquet, a few narrow numeric cols) -> modelScore(prediction) or scenarioExpander or a polars with_columns that builds a wide String column (e.g. concat_str of several fields) feeding the target. _plan_chunk_sizes computes target_row_bytes = _estimate_projected_row_bytes(target_columns, source_node=<the dataSource>). _source_projected_column_widths returns {} for every column NOT present in the source schema, and _estimate_projected_row_bytes then assigns _DEFAULT_PROJECTED_COLUMN_BYTES (64) per such column. A produced String column averaging, say, 2KB/row is costed at 64 bytes — a 30x under-estimate. chunk_size = target_chunk_bytes // target_row_bytes is therefore ~30x too large, and the materialized target chunk (streaming_collect at chunking.py:1029) holds ~30x the intended bytes, breaking the bounded-memory contract the chunked path promises and the admission budget assumes.
- **Evidence:** Executed repro output: `estimated_target_row_bytes = 72` (= 8 for Int64 `id` from source + 64 fallback for the downstream-created String column `big`), while the REAL per-row width of `big` is ~2004 B and the real full row ~2012 B -> a 27.9x under-count. The plan chose `chunk_size = 13888`, so the materialized target chunk projects to ~27.9 MB against the stated `target_chunk_bytes = 1_000_000` (1 MB) budget — a ~28x overshoot. Code-trace confirms the mechanism with no downstream guard: chunking.py:608 `target_columns = projection.needed_by_node.get(request.target_node_id)` returns {id, big}; chunking.py:609-613 calls `_estimate_projected_row_bytes(target_columns, source_node=<dataSource>)`; `_source_projected_column_widths` (654-659) only inspects the dataSource schema and returns {} for any column not in it, so 648-651 assigns `_DEFAULT_PROJECTED_COLUMN_BYTES = 64` (chunking.py:180) to `big`. projection.py:1149 (`demand = (demand - outputs) | refs`) proves the derived `big` is NOT propagated to the source demand, so it can never appear in the source schema width map. The runner at chunking.py:1029 does `streaming_collect(target_lf, ...)` fully materializing the oversized chunk into the yielded `pl.DataFrame` with no byte cap or re-costing. The pre-existing test `test_byte_budgeted_chunk_plan_shrinks_wide_projected_schema` (tests/test_chunk_plan.py:156) only exercises wide columns that exist IN the source, so this downstream-created case is untested.
- **Fix:** Cost the target row width from the TARGET node's actual output schema, not the source schema. Options: (a) derive a projected output schema by lazily building the chunk suffix (collect_schema on the target lazyframe restricted to needed_by_node[target]) and map dtypes via _dtype_estimated_width, sampling String/variable-width columns the same way _source_projected_column_widths samples the source; or (b) if a produced column's width cannot be proven (no concrete dtype/sample available), fail loud with ChunkPlanUnsupportedError rather than silently applying the 64 B default — consistent with the module's fail-loud stance and the project rule against silent fallbacks. A regression test mirroring the repro (downstream-created wide String column, assert estimated_target_row_bytes reflects ~2 KB and chunk_size keeps projected chunk bytes <= target_chunk_bytes) should pin it.
- **Repro:** `execution__chunk-byte-budget-undercounts-downstream-created-columns.py` - EXIT=0 (bug reproduced). Key lines: `estimated_target_row_bytes = 72`; `chunk_size = 13888`; `REAL big per-row bytes = 2004`; `under-count factor = 27.9x`; `projected chunk bytes = 27938892 (budget 1000000)`.
