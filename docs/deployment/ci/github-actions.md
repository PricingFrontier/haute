# GitHub Actions

This guide explains the GitHub Actions starter workflows generated by `haute init`. They run validation and deployment commands, but GitHub repository settings—not Haute—control branch protection, environment approval, and who may run production deployment. Databricks is the only end-to-end service-update adapter; generic container builds/pushes only, and Azure Container Apps, AWS ECS, and GCP Cloud Run build and push the image and leave the service update to you.

!!! tip "New to Git, pull requests, or CI/CD?"
    This page assumes you understand basic Git concepts like branches, commits, and pull requests. If these are unfamiliar, read [Before You Start](../before-you-start.md) first - it explains everything in plain English.

!!! tip "Not sure if this is the right page?"
    If you access your project on **github.com**, this is the right page. If it's on **gitlab.com** (or a company GitLab server), go to [GitLab CI/CD](gitlab.md). If it's on **dev.azure.com**, go to [Azure DevOps](azure-devops.md). If you're not sure, ask your IT team or tech lead: *"Where is our code repository hosted?"* They'll tell you GitHub, GitLab, or Azure DevOps.

!!! info "What is CI/CD?"
    **CI** (Continuous Integration) means your code is automatically tested every time you propose a change. **CD** (Continuous Deployment) means the workflow can run a deployment step after those tests pass. A live endpoint is created or updated only when the selected target and hosting process support it. See [full explanation](../before-you-start.md#what-is-cicd).

!!! warning "Read this before enabling the starter workflows"
    The files are examples that call `haute deploy`, `haute smoke`, and `haute impact` in order. Haute does not create staging infrastructure, require an approval, or guarantee an impact report. On Databricks, `haute deploy` returns once the endpoint serves the new version, and fails with Databricks' reason when it cannot. A failed deploy prevents dependent smoke and impact jobs. For platform-container targets, the deploy job succeeds once the image is pushed and prints its tag for your manual platform update; their generated workflow has no smoke or impact job, because nothing runs the new image until you update the service.

    On container targets, the deploy jobs log in to the `registry` in `haute.toml` before they push, and the smoke and impact steps need [the service addresses](../targets/docker.md#step-3-give-smoke-and-impact-their-endpoints) in `haute.toml`. The impact step compares a [portfolio sample in the repository](../targets/databricks.md#what-each-setting-means) when you name one, and your test quotes until you do.

!!! info "What is GitHub Actions?"
    GitHub Actions is GitHub's built-in automation tool. It runs scripts (called **workflows**) in response to events in your [repository](../before-you-start.md#getting-your-project-ready-for-deployment) - like opening a pull request or merging to the main branch. It's free for public repositories and has a generous free tier for private ones.

!!! note "Who does what on this page?"
    This page has **two parts**. As a pricing analyst, you only need to do **Step 2** (commit the workflow files) and **Step 3** (test it). **Step 1** (adding secrets) is usually done by your IT team or tech lead - they have the credentials and know the GitHub UI. If you're setting this up yourself, Step 1 walks you through it, but it's perfectly fine to hand it to IT and say: *"Can you add these secrets to our GitHub repository? Here's the `.env.example` file listing what's needed."*

## What Haute generates

When you run `haute init --ci github`, Haute creates three workflow files in `.github/workflows/`:

| File | When it runs | What it does |
|---|---|---|
| `ci.yml` | On every pull request | Lints, type-checks, runs tests, validates your pipeline |
| `deploy-staging.yml` | On a push to main or manual dispatch | Runs validation, then deploy/smoke/impact commands in dependency order |
| `deploy-production.yml` | When you click "Run workflow" manually | Runs `haute deploy` for production; configure GitHub protections if approval is required |

This gives you a complete release pipeline:

```
Pull request → CI checks → Merge → target-dependent staging deploy → smoke/impact only if deploy succeeds → [your GitHub approval process] → manually triggered production deploy
```

### Workbench projects

A [workbench project](../../building-models/workbench.md) hosts no API: what it releases is
the [underwriter app](../../building-models/workbench.md#the-underwriter-app). Its
`haute init` writes three workflow files instead:

| File | When it runs | What it does |
|---|---|---|
| `ci.yml` | On every pull request | Lints, type-checks and runs tests, then builds the app's release, which checks your pipeline and schema and scores your test quotes |
| `release.yml` | On a push to main or manual dispatch | Runs the same checks, then, on main only, builds the app's image once, pushes it to the registry `[deploy.container]` names, and rolls the staging app out to it |
| `release-production.yml` | When you click "Run workflow" manually | Rolls the production app out to the release staging runs, for the commit you give (main's head when blank) |

Each rollout stops the old release before the new one starts, checks the app, and puts the
previous release back when the new one fails
([The underwriter app](../../building-models/workbench.md#the-underwriter-app)). One rollout
of an environment runs at a time. The jobs read your host's secrets,
`AZURE_SUBSCRIPTION_ID`, `AZURE_TENANT_ID`, `AZURE_CLIENT_ID` and `AZURE_CLIENT_SECRET`,
which `haute ci secrets` sets from `.env`; the service principal needs the AcrPush role on
the registry.

## How it works, step by step

### 1. You make a change and open a pull request

You edit your pipeline, update a model, or change a configuration. You push your changes to a [branch](../before-you-start.md#1-create-a-branch) and open a [pull request](../before-you-start.md#4-ask-for-a-review-pull-request) (PR) on GitHub - which is a way of asking your teammate to review your changes before they go live.

### 2. CI runs automatically

The `ci.yml` workflow runs immediately:

- **Lint & format** - checks your code style with `ruff`
- **Type check** - runs `mypy` to catch type errors
- **Tests** - runs `pytest`
- **Pipeline validation** - runs `haute lint` and `haute deploy --dry-run` to check your pipeline parses correctly and test quotes pass

If any of these fail, the PR gets a red ❌ and you can see what went wrong.

### 3. You merge to main

Once CI passes and your teammate has reviewed the PR, you [merge](../before-you-start.md#5-accept-the-changes-merge) it - which applies your changes to the main version of the project. This triggers the `deploy-staging.yml` workflow (named **Deploy**) when the merge changes the pipeline, its configuration, data, models or test quotes.

### 4. Staging deployment (automatic)

The deploy workflow:

1. **Validates** again (lint, type check, tests, `haute lint` and a dry-run deploy)
2. **Deploys to staging** - runs `haute deploy --endpoint-suffix "-staging"`. On Databricks it waits until the staging endpoint serves the new version, and fails with Databricks' build log if the model cannot be served; the generic container target does not host an endpoint; platform-container targets push the image and leave the service update to you, so their workflow ends there.
3. **Smoke tests staging** - only after a successful deploy, runs `haute smoke --endpoint-suffix "-staging"` against an existing live endpoint; on the generic container target it runs `haute smoke`, which calls [the staging address in `haute.toml`](../targets/docker.md#step-3-give-smoke-and-impact-their-endpoints)
4. **Runs impact analysis** - only after smoke succeeds, runs `haute impact --endpoint-suffix "-staging"` against existing staging and production endpoints; on the generic container target, `haute impact` at the addresses in `haute.toml`

When the impact command runs, its report is uploaded as the `impact-report` artifact and added to the run's summary page; it is not produced when an earlier stage fails.

### 5. You review the impact report

The impact report shows you exactly what changed, for each output column:

```
  Output: technical_price
  ────────────────────────────────────────────────────────────
  Staging mean:          548.57     Production mean: 536.12
  Rows changed:           8,420 / 10,000 (84.2%)
  Mean change:            +2.3%
  Median change:          +1.9%
  Premium impact:         +2.3%
  Max increase:          +18.7%
  Max decrease:           -4.2%

  Distribution:  P5=-0.8%  P25=+0.6%  P50=+1.9%  P75=+3.4%  P95=+7.1%
```

Segment tables follow, one for each text column of the portfolio sample with 2 to 50 values, listing the segments whose prices move most. Without a portfolio sample (`[safety] impact_dataset`), the report compares your test quotes and says so. The report is advisory: it never fails the job, so reading it is your decision point.

This is where you decide: does this change make sense? Is the impact expected?

### 6. You promote to production (manual)

If you're happy with the impact report, go to the **Actions** tab in GitHub, find the `Deploy → Production` workflow, and click **Run workflow**.

You can optionally paste the git SHA from the staging deploy to make sure you're deploying exactly what was tested - not something that was merged since.

The production workflow runs `haute deploy` and then tags the release. Its ability to update a live endpoint depends on the selected target; configure GitHub environments/branch protections separately if this action needs approval.

## Setup

### Step 1: Add your credentials as GitHub Secrets

!!! tip "This step is usually done by IT"
    If you're not comfortable navigating GitHub's settings, ask your IT team or tech lead to do this. Give them the `.env.example` file from your project - it lists exactly which secrets are needed.

Your CI/CD workflows need credentials stored securely in GitHub.

**The quickest way: let Haute set them.** Copy `.env.example` to `.env` and fill in the values, and sign in to the [GitHub CLI](https://cli.github.com) once with `gh auth login`. Then either:

- **Push from the editor.** The Push that first publishes your project to a new, empty GitHub repository also stores the secrets your deploy target needs, before your `main` branch arrives, so the first deploy has them. If that Push couldn't set them, a message says why. Whenever a later Push finds the repository missing some, the Git panel shows how many beside a **Set from .env** button.
- **Run `haute ci secrets` in your project.**

Either way Haute reads the secrets from `.env`, checks that Databricks accepts them, and stores them as encrypted repository secrets, never printing their values. The editor only adds secrets the repository doesn't have yet; to replace one, for example after rotating a token, run `haute ci secrets`. `haute ci secrets --check` lists which the repository has.

**Or add them by hand:**

1. Go to your repository page on GitHub (e.g. `github.com/yourcompany/motor-pricing`)
2. Click the **⚙️ Settings** tab (near the top of the page, next to "Insights")
3. In the left sidebar, click **Secrets and variables** → **Actions**
4. Click the green **New repository secret** button
5. For each credential below, enter the **Name** and **Secret** value, then click **Add secret**:

**For Databricks:**

| Secret name | Value |
|---|---|
| `DATABRICKS_MLFLOW_HOST` | The workspace URL for MLflow and the model registry |
| `DATABRICKS_MLFLOW_TOKEN` | A personal access token scoped for MLflow and the model registry |
| `DATABRICKS_RATING_HOST` | Your workspace URL (e.g. `https://adb-xxx.12.azuredatabricks.net`) |
| `DATABRICKS_RATING_TOKEN` | Your personal access token (starts with `dapi`) scoped for Model Serving |

**For Docker/Container targets:**

| Secret name | Value |
|---|---|
| `DOCKER_USERNAME` | Your registry username |
| `DOCKER_PASSWORD` | Your registry password or access token |

**For AWS ECS:**

| Secret name | Value |
|---|---|
| `AWS_ACCESS_KEY_ID` | Your AWS access key |
| `AWS_SECRET_ACCESS_KEY` | Your AWS secret key |
| `AWS_DEFAULT_REGION` | e.g. `eu-west-1` |

ECR passwords last 12 hours, so the deploy jobs fetch a fresh one with these keys each run (see [AWS ECS](../targets/aws.md#step-2-add-credentials-to-ci)).

**For Azure Container Apps:**

| Secret name | Value |
|---|---|
| `AZURE_SUBSCRIPTION_ID` | Your Azure subscription ID |
| `AZURE_TENANT_ID` | Your Azure tenant ID |
| `AZURE_CLIENT_ID` | Your service principal app ID |
| `AZURE_CLIENT_SECRET` | Your service principal password |

The deploy jobs log in to ACR as the service principal (see [Azure Container Apps](../targets/azure.md#step-2-add-credentials-to-ci)).

!!! tip "How to find these values"
    These are listed in the `.env.example` file that `haute init` generated in your project. Your target's setup page explains where each value comes from.

### Step 2: Commit the workflow files

The workflow files were created by `haute init` in `.github/workflows/`. Make sure they're committed to your [repository](../before-you-start.md#getting-your-project-ready-for-deployment):

```powershell
git add .github/ pyproject.toml uv.lock
git commit -m "Add CI/CD workflows"
git push
```

Every job installs with `uv sync --frozen`, which needs the project's `uv.lock`: commit it with `pyproject.toml`. `uv add` creates it; run `uv sync` once if it is missing.

!!! note "What do these commands mean?"
    - `git add` - tells Git to include these files in your next save
    - `git commit -m "..."` - saves a checkpoint with a description
    - `git push` - uploads the changes to the shared copy (GitHub)

    See [Git workflow](../before-you-start.md#git-workflow-branches-pull-requests-and-merging) for a full explanation.

### Step 3: Test it

1. Create a [branch](../before-you-start.md#1-create-a-branch), make a small change, and open a [pull request](../before-you-start.md#4-ask-for-a-review-pull-request)
2. Watch the **Actions** tab - the CI workflow should start automatically
3. If it passes, [merge](../before-you-start.md#5-accept-the-changes-merge) the PR
4. Watch the deploy workflow run - it should deploy to staging and generate an impact report

## The generated workflows in detail

!!! note "You don't need to read or understand the YAML below"
    The workflow files were generated by `haute init` and work out of the box. The sections below are **reference only** - for troubleshooting or if your IT team wants to understand what’s happening.

??? info "`ci.yml` - Pull request checks"

    ```yaml
    name: CI

    on:
      pull_request:
        branches: [main]

    jobs:
      lint:
        # Runs ruff check and ruff format --check
      typecheck:
        # Runs mypy
      test:
        # Runs pytest
      pipeline-validate:
        # Runs haute lint and haute deploy --dry-run
    ```

    This runs on every pull request targeting `main`. All four jobs run in parallel for speed.

??? info "`deploy-staging.yml` - Merge to main"

    ```yaml
    name: Deploy

    on:
      push:
        branches: [main]
        paths:
          - "rating/**"
          - "tests/quotes/**"
          - "haute.toml"
          - "pyproject.toml"
          - "uv.lock"
      workflow_dispatch:

    jobs:
      validate:     # ruff check, mypy, pytest, haute lint, dry-run deploy
      deploy-staging:  # haute deploy --endpoint-suffix "-staging"
      smoke-test:      # haute smoke --endpoint-suffix "-staging" (container: haute smoke)
      impact-analysis: # haute impact --endpoint-suffix "-staging" (container: haute impact)
    ```

    A push to main triggers it only when relevant files change (the `rating/` pipeline package, config, data, models, test quotes, and the dependency files `pyproject.toml` and `uv.lock`; a workbench's files are in the pipeline package, so a change to them deploys too); you can also run it by hand from the **Actions** tab. Jobs run in sequence - if staging fails, smoke test doesn’t run.

??? info "`deploy-production.yml` - Manual production deploy"

    ```yaml
    name: Deploy → Production

    on:
      workflow_dispatch:
        inputs:
          sha:
            description: Git SHA that was staged & impact-analysed
            required: false

    jobs:
      deploy-production:
        # Verifies SHA matches (if provided)
        # Runs haute deploy (no suffix = production)
        # Tags the release in Git
    ```

    This is triggered manually from the GitHub Actions UI. The optional SHA input lets you pin the exact commit that was tested.

## Working solo?

If you're the only person on the team, the process is the same but simpler:

1. `min_approvers` in `haute.toml` is not enforced by Haute; configure GitHub environment or branch rules for any required approvers
2. The generated workflow attempts CI → staging → smoke test → impact analysis → manual production deploy; later jobs require a ready endpoint and do not run after a failed deploy
3. An impact report is generated only when the impact command runs successfully

## Troubleshooting

### Workflow doesn't trigger

- **On PR:** Make sure the PR targets the `main` branch (not another branch)
- **On merge:** Make sure the `deploy-staging.yml` paths filter matches your changed files. If you only changed a markdown file, it won't trigger (by design)
- **Check the Actions tab:** Go to your repo → **Actions** → look for the workflow run
- **Nothing has ever run in a new repository:** if **Run workflow** works but no push or pull request has ever started a run, the repository's first push created more than one branch. GitHub never runs workflows from pushes or pull requests in such a repository, and later pushes do not change that. Haute 0.6.0 and earlier pushed like this the first time you pushed a project to an empty repository; later versions publish `main` on its own first. Create a new, empty repository and push the project to it. If you create a repository's first branch yourself, push `main` on its own first (`git push origin main`)

### "Credentials not found" or "Authentication failed"

Your GitHub Secrets are missing or misnamed. On Databricks, `haute deploy` names every missing one before it does anything else, and `haute ci secrets --check` lists which the repository has. Double-check:

1. Go to **Settings** → **Secrets and variables** → **Actions**
2. Verify the secret names match exactly (they're case-sensitive)
3. Verify the values are correct (no trailing spaces or newlines)

### Deploy workflow succeeds but endpoint isn't updated

Check the deploy step logs in the Actions run. For Azure Container Apps, AWS ECS and GCP Cloud Run this is expected: the log ends with `Image pushed:` and `The <target> service was not updated`, and you point the service at that image yourself (see your target's documentation).

### Impact analysis shows unexpected results

The impact analysis compares staging vs production. On a first deploy, a missing production endpoint is recorded as a first-deployment report; a missing or unready **staging** endpoint is still a real failure. Make sure staging is ready before the impact job runs.

### "HEAD (...) does not match staged SHA (...)"

This error in the production workflow ("Merge may have occurred since staging.") means someone merged another PR between your staging deploy and your production deploy. The production workflow is protecting you from deploying untested code. Run the staging deploy again (push to main or re-run the deploy workflow) and then try production again.

### The tag step fails

On Databricks, the production workflow's **Tag release** step names the tag after the latest registered model version, which it reads with `haute status`, using the same secrets as the deploy step. If the version cannot be read, the step fails with the reason instead of tagging a made-up version.

A workflow generated by an older Haute gave this step no credentials, so it tagged `deploy/vunknown` and the next production run failed on that existing tag. Run `haute ci update` to regenerate the workflows, and delete the `deploy/vunknown` tag.

### Keeping the workflow files up to date

The workflow files are generated by the Haute version that ran `haute init`. After upgrading Haute, run `haute ci update`: it rewrites the generated workflow files and `.env.example` for the installed version and leaves everything else alone. Review the change with `git diff`, then commit it.
