# G09 — Pin `LC_ALL=C` and classify foreseeable git failures into domain errors

**Severity: MEDIUM (breaks a HIGH-value UX path on non-English machines) · Confidence: CONFIRMED**
**Files: `src/haute/_git.py`**
**Origin: R-2, R-3 (routes reviewer), T-1 (tests reviewer), engine reviewer's gettext analysis. Independently verified: no `LC_ALL`/`LANG` pinning anywhere in `src/`.**

## R-2 / T-1 — the push-rejection classifier is locale-dependent

`push_working_pair` classifies rejections by English substrings (`_git.py:2172`):

```python
if any(s in stderr for s in ("non-fast-forward", "fetch first", "[rejected]")):
```

Engine reviewer confirmed all three tokens are gettext-wrapped in git's human push-status output
(`transport.c`), and Git-for-Windows ships translation catalogs selected by the Windows UI locale.
On a German/French/Spanish machine a real non-fast-forward push does not match → falls through to
`raise GitError(stderr)` → sanitized **400** instead of the structured **409 GitPushRejection**.
The entire M7 fork-resolution UX (the panel's best moment — per-leg divergence + catch-up/spin-off
options) silently never fires for those users. `_run_git` (`_git.py:194-202`) builds env as
`{**os.environ, **env}` with no locale pin.

Nuance worth keeping (engine reviewer): the unborn-seed **identity detector**
(`_git.py:1039-1047`) is already localization-robust — `"user.email"`/`"user.name"` are literal
config keys inside git's hint and are never translated — so it works either way, but pinning makes
it uniformly testable.

**Fix.** Pin `LC_ALL=C` (and `LANG=C`) in one place for every git subprocess: `_run_git`,
`_run_git_ok`, and the four ad-hoc `subprocess.run` sites (`_fetch_refs` `_git.py:254-258`,
`_ls_remote_version_tags` `:2061-2065`, `push_working_pair` `:2165-2168`, `archive_commit`
`:1839-1843`). Order matters: user env first, pins last so they always win. This is the
prerequisite for R-3 below — never add another stderr classifier without it.

## R-3 — foreseeable failures all collapse to the generic sanitized 400

`_handle_git_error` maps any plain `GitError` → `_INTERNAL_ERROR_DETAIL` (`routes/git.py:117-118`).
Correct as a default (stderr can leak paths/URLs/credentials), but these user-caused,
user-fixable failures deserve hand-written classification (stable `LC_ALL=C` tokens → messages):

| stderr token (C locale) | Trigger a pricing user actually hits | Proposed `GitDomainError` copy |
|---|---|---|
| `Permission denied` / `unable to unlink` | **A generated CSV/xlsx open in Excel** during move / fast-forward / branch-away tree swap | "A file in this project is open in another program (often Excel). Close it and try again." |
| `index.lock` … `File exists` | Another git process (IDE, `git gui`, or a pre-G01 race) | "Another program is using this repository's version control right now. Close other git tools and retry." |
| `would be overwritten by checkout` | Untracked files colliding with the target tree on move/ff (the dirty-gate uses `--untracked-files=no`, so this is not pre-screened — `_git.py:1187`) | "Files that aren't in version control would be overwritten: <first few names>. Move them aside and retry." |
| pre-commit hook failure on the ledger commit | Repo hooks rejecting the autogenerated save commit | Save warning names the hook: "Changes saved; version capture was blocked by this repository's pre-commit hook." |

Implementation shape: a small `_classify_git_error(stderr) -> GitDomainError | None` used by
`_run_git`'s raise site (and the push path after the rejection check), so classification is
uniform and logged with the raw stderr intact. Do **not** weaken the default sanitization — the
allowlist maps to fixed hand-written strings; file names may be included only after passing the
same repo-relative check the save path uses.
