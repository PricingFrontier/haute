# Opus 5 review — `docs/specs` corpus

A full engineering review of all 68 documents under `docs/specs/` (33 components × high-level +
low-level, plus `README.md`, `TEMPLATE.md`, `ownership.toml`), read in full and cross-checked
against the source they describe.

Because these specs are written to describe the code **as it is**, a defect described in a spec is
a defect in the *system*, and a claim the code contradicts is a defect in the *spec*. This review
hunts both, plus the inconsistencies, brittleness and over-complication the corpus reveals.

---

## Executive summary

The corpus is structurally excellent and substantively out of date. The writing discipline, the
`> NOTE:` convention for flagging suspected defects, the machine-checked ownership ledger, and the
100%-complete module-map coverage of source files are genuinely better than most production
codebases achieve. Preserve all of that.

The problem is that **the corpus has no mechanism for retiring a statement once it becomes false**,
and after several shipped releases that has compounded into a document set an engineer cannot
safely trust:

1. **The temporary layer has become the largest layer.** `## Approved change contract` now appears
   **59 times** across the corpus, and `## Polars backend contracts (0.6.0)` a further **31** —
   against **33** occurrences of each *required* section. `TEMPLATE.md:76-79` states that when a
   change ships, its contract must be folded into the present-tense sections and the temporary
   section **removed**. Nothing enforces this, and a large fraction of those 59 sections describe
   work that has demonstrably shipped.

2. **Reconciliation, where it happened, went both ways and finished neither.** Shipped behaviour is
   documented *only* inside sections labelled "future" (the shared source-snapshot cache, the
   lineage cache-key factory, `TraceCorrelationUnsupportedError`, two public rating errors, the
   OUTPUT fail-loud guards). Removed behaviour is *still* documented in present tense
   (`safe_sink`/`best_effort_sink`, the `data_source`/`data_sink` decorators,
   `executor.execute_sink`). And `io-layer/high-level.md:287` tells the reader that "the
   present-tense sections above continue to describe the shipped implementation" when those
   sections have **already** been rewritten to the post-0.7.0 behaviour.

3. **One whole component's specification is fiction.** Every present-tense section of both
   `databricks-io` documents — Purpose, Behaviour, Interactions, Failure model, Module map, Key
   types, Control flow, Edge cases, Error handling, Testing — describes a fetch/cache API and an
   HTTP route family that were deleted. The shipped surface (`DatabricksSnapshotBuilder`) appears
   nowhere outside a temporary contract section.

4. **The guard rail is much narrower than the contract it appears to enforce.**
   `tests/test_docs_accuracy.py` has 21 tests and they all pass — but `_low_level_spec_references()`
   only reads inline-code spans from the **first cell of table rows inside `## Module map`**.
   Everything else in all 68 documents is unvalidated. That single scope decision is why the
   corpus is green in CI while a component's entire spec is wrong.

5. **The specs describe fail-loud behaviour that the code does not implement.** `AGENTS.md:5`
   forbids speculative or silent fallbacks. 132 of the verified findings are outright bugs, and the
   dominant shape is a silently swallowed failure in a path the spec calls loud — including several
   that end in **data loss on the user's disk**.

6. **Version stamps track nothing.** `pyproject.toml` is `0.4.0`, `src/haute/server.py:383`
   declares the API as `0.1.0`, there are no git tags, and the specs carry 0.6.0, 0.7.0 and 0.8.0
   contracts. `## Polars backend contracts (0.6.0)` is defined by neither `TEMPLATE.md` nor
   `README.md` and has no removal rule at all.

The single highest-leverage fix is not any individual bug: it is **extending the docs-accuracy
guard to the whole document and forcing the contract sections to be retired**. Until that lands,
every correction made here will silently rot again.

## Method and confidence

- All 68 documents were read in full by a per-component auditor that also opened the source files
  named in each Module map and verified symbols, routes, defaults, limits, error types and
  claimed invariants against the code.
- Seven further sweeps read *across* components: contract staleness classification (shipped /
  partial / pending), execution and I/O seam coherence, failure-model coherence against
  `AGENTS.md`, over-complication and brittleness, Testing-section credibility, and corpus-level
  coherence of `README.md` / `TEMPLATE.md` / `ownership.toml` / `docs/roadmap`.
- **Every finding then went through an adversarial verification pass whose default verdict was
  *refuted*.** A finding survived only if a second reader personally opened the evidence and it
  held. **70 of 531 raised findings were refuted and are excluded from this document.** The
  severity and evidence shown below are the verifier's corrected values, not the reporter's.
- Independent sweeps were allowed to overlap, and where they converged on the same defect from
  different angles both findings are kept — that convergence is signal, not duplication.
  `databricks-io` is the clearest case: five separate readers reached it via the module surface,
  the Testing section, the Failure model, the high-level Behaviour, and the contract inversion.
- Deterministic checks (section conformance, link and anchor integrity, module-map path existence,
  `path::symbol` resolution, ownership-ledger agreement, and a comparison of every API path claimed
  in the specs against the live FastAPI route table) were run directly rather than delegated.

**What this review is not.** It is a review of the specifications and of the code they name. It is
not a full independent audit of the codebase; a module no spec discusses in depth was not read in
depth. No code was changed.

**Deliberately excluded as noise:** API route contracts are clean — all seven apparent mismatches
resolve to router prefixes, a `> NOTE:` about endpoints deliberately never built, or removals the
code confirms. Relative-link integrity is 100% (0 broken of all links checked, including anchors).
Backend module-map coverage is complete (0 of 176 backend sources uncovered; 1 of 267 frontend
sources, and that one is deliberately excluded as test setup). The `ownership.toml` ledger is
correct *within its documented scope*, so an earlier prose-inclusive scan's 60 "undeclared shared
files" were false positives and are not reported.

## The six systemic problems

### S1. The temporary layer outgrew the permanent one

`TEMPLATE.md:76-79` is unambiguous: an `## Approved change contract` states approved *future*
behaviour, and "the implementation/release change must reconcile the approved contract into the
normal sections and remove the temporary section."

Current state of the corpus:

| Section | Occurrences |
|---|---:|
| `## Approved change contract …` | 59 |
| `## Polars backend contracts (0.6.0)` | 31 |
| Each *required* section (`## Purpose`, `## Behaviour`, …) | 33 |

Two dozen components carry at least one. The audit classified them and found sections that have
**fully shipped** and still sit under a future-tense heading — including `server-api`'s bounded
request correlation, `cli`'s local UI serving, `modelling`'s 0.8.0 isolated fit,
`execution-engine`'s 0.8.0 worker transport, `frontend-graph-canvas`'s live-update reconciliation,
and `io-layer`'s partitioned-Parquet boundary. Others are **partial**, with shipped and unshipped
clauses interleaved and nothing marking the split (`frontend-trace-ui`, `tracing`, `assistant`).

The consequence is concrete. `AGENTS.md:7` instructs engineers to define functionality changes in
`docs/specs` before changing code. An engineer doing that today cannot determine, from the document
alone, which half of it is true.

### S2. Reconciliation ran in both directions and completed neither

- **Shipped behaviour visible only in the "future" section.** `caching`'s own Scope and Module map
  omit the shared source-snapshot cache that has shipped; it exists only inside the contract.
  `tracing`'s `TraceCorrelationUnsupportedError` is shipped and route-mapped but documented only
  under "Polars backend contracts (0.6.0)". `rating` has two shipped public errors that appear in
  neither present-tense failure section.
- **Removed behaviour still documented as live.** `io-layer`'s Error-handling table promises a
  `ValueError` from `_polars_utils.best_effort_sink`; that function was deleted, and
  `tests/test_bounded_sink_contract.py` actively asserts its absence. `pipeline-config`'s Behaviour
  section still lists `data_source` and `data_sink` decorators. `execution-engine` names
  `executor.execute_sink`, which is now `write_data_output`.
- **A document that misdescribes its own state.** `io-layer/high-level.md:287` states the sections
  above it still describe pre-0.7.0 behaviour. They do not — they were already rewritten.

### S3. The docs-accuracy guard validates a small fraction of what the corpus claims

`tests/test_docs_accuracy.py` is a good idea implemented too narrowly. `_module_map_file_references()`
(`:408-417`) takes `row.group(1)` — the **first cell** — of rows matched by
`_MODULE_MAP_ROW` (`:45`), and `_module_map_text()` (`:370-376`) restricts that to the `## Module map`
section. Therefore:

| Claim made in a spec | Validated? |
|---|---|
| A file path in a Module map's first cell | Yes |
| A symbol list in a Module map's **second** cell | **No** — this is how `best_effort_sink` survived in an Error-handling table |
| A test file or test class in a `## Testing` section | **No** — `tests/test_databricks_cache.py` does not exist; ~10 further test identifiers in that one component do not exist |
| A path in prose or in a contract section | **No** |
| A link's `#anchor` | **No** — `:728` strips the fragment before checking |
| Presence of required sections | Yes, but by `heading in text` substring (`:716`), not by heading |
| **Absence of a shipped temporary contract** | **No rule exists** |

Two components additionally assert "no coverage gaps identified" while their own file lists are
demonstrably incomplete, and roughly 90 of the 399 backend test files are named in no spec at all.

### S4. Silent fallbacks in paths the specs call loud

`AGENTS.md:5`: "Do not add speculative or silent fallbacks. Let unexpected states fail clearly so
the underlying defect can be found and fixed." The verified bug list is dominated by violations,
several of which lose user data:

- `frontend/src/hooks/useWebSocketSync.ts:261-267,317-328` drops the incoming `submodels` map from a
  `graph_update`, then calls `markSaved()`. The next save writes the stale map back over the user's
  externally-edited file.
- `src/haute/routes/pipeline.py:424-447` catches `Exception` on every parse and returns an empty
  `PipelineGraph()`. A syntax error in `main.py` presents as a blank canvas with no error; saving
  from that state overwrites the file. The by-name route `get_pipeline` correctly 404s, which makes
  the inconsistency worse.
- `src/haute/_flatten.py:86-88` — `# Skip edges that still reference a submodel node (shouldn't
  happen)` followed by `continue`. `routes/submodel.py:192` runs this in the dissolve path and
  **persists** the result, so a dropped edge becomes permanent loss.
- `haute init` unconditionally deletes the user's root `main.py`.
- Codegen re-emits preserve blocks once per save (unbounded file growth), relocates an indented
  preserve block to module level (permanently blocking every future save), and regenerates submodel
  files without preamble or preserved blocks (discarding hand-authored module code).
- Cancelled or timed-out training still overwrites the durable model and feature contract.
- Databricks deploy serves model version `"1"` when the registry returns no versions.
- The expression evaluator returns the receiver's value for any unsupported method, fabricating
  confident but wrong trace output.

### S5. One responsibility, several implementations

28 verified over-complication findings. The recurring shape is a second implementation that the
spec documents while production uses the first — or vice versa:

- **Four** independent background-job polling loops in the frontend with four different
  cancellation, backoff and timeout policies; the one in `api/client.ts` has no production caller.
- `OptimiserSolveService` runs **three** `CancellableJobRegistry` instances plus a
  `SingleFlightCoordinator` keyed identically to one of them, released by hand at eight sites.
- Two process-isolation runners — and the spec documents the one with no production caller.
- Two graph builders: `Pipeline.to_graph()` has different node-type and edge inference from
  `_graph_builders.py` and zero production callers.
- `json_cache.py` reimplements a job registry that `input_cache.py` already gets from the shared
  `JobStore`, and its `cancel` endpoint is a stub behind a live Cancel button in the UI.
- The bounded-memory profile policy is implemented twice with two identically-valued frozensets and
  three copies of `_normalise_profile`, with no test that they agree.
- The Python hard-keyword list is hand-copied four times in the frontend, and the tests compare each
  copy against another hand-written copy.

Two god modules anchor this: `src/haute/routes/_optimiser_service.py` at **5,336 lines** (its own
spec lists eight unrelated responsibilities), and `src/haute/execution.py` at **1,203 lines** while
documented as a thin re-export facade.

### S6. Version stamps that correspond to nothing

`pyproject.toml` is `0.4.0`; `src/haute/server.py:383` declares the FastAPI app as `0.1.0`; there
are no git tags; the specs carry 0.6.0, 0.7.0 and 0.8.0 contracts. `## Polars backend contracts
(0.6.0)` appears in 31 files and is described by neither `TEMPLATE.md` nor `README.md`, so no rule
says when it may be deleted. The roadmap compounds this: its index's "Start with" column names
already-delivered packages, three roadmaps retain 100%-delivered work against their own removal
rule, six spec sections route readers to roadmaps that state in writing they contain no work, and
39 roadmap "Evidence:" paths point at files that do not exist.

## Recommended sequence

**Wave 0 — make the corpus trustworthy again.** Cheap, and everything else rots without it.

1. Extend `tests/test_docs_accuracy.py` beyond Module-map first cells: validate every inline-code
   repo path in the **whole document**, resolve `path::symbol` references to a real symbol, check
   link `#anchor`s, and make the structure check heading-based rather than substring-based.
2. Add the missing rule: a `## Approved change contract` may not survive once the symbols, routes
   or files it names have reached the state it describes as its target. Make CI say so.
3. Sweep all 59 contract sections and all 31 `(0.6.0)` sections: fold the shipped ones into the
   present-tense text and delete them, split the partial ones, keep only what is genuinely pending.
4. Rewrite both `databricks-io` documents from the code as it stands today.
5. Decide what the version stamps mean, or remove them. Align `pyproject.toml` and
   `server.py:383`.

**Wave 1 — the bugs that lose user data**, in this order: `frontend-graph-canvas-1` (submodel
overwrite), `cli-2` (`haute init` deletes `main.py`), `codegen-1/2/3` (preserve-block growth,
permanent save block, discarded submodel code), `failure-model-3` (dissolve drops edges),
`failure-model-2` (blank-canvas overwrite), `frontend-git-ui-1` (branch ops discard unsaved edits),
`modelling-1` (cancelled training overwrites the durable model), `submodels-2`.

**Wave 2 — security and concurrency**: `sandbox-security-1` (the `str.format` dunder guard is
bypassable with a nested format spec), the two credential-in-query-string findings, the checkpoint
filename traversal, then the races — `server-api-1`, `optimiser-2`, `deploy-1`, `io-layer-9`, and
the unlocked `_ensure_module_deps` twin.

**Wave 3 — the remaining silent fallbacks**, swept as one campaign against `AGENTS.md:5` rather
than one at a time.

**Wave 4 — consolidation**: the 28 over-complication findings, starting with the four job-polling
loops and the optimiser's four concurrency structures, then splitting the two god modules.

## Critical and high findings (in full)

Every finding below survived an adversarial verification pass in which the default
verdict was *refuted*. Evidence is the tightest `path:line` the verifier could confirm.

### Critical (3)

#### `databricks-io-1` — Both spec files document a Databricks fetch/cache API that was deleted in commit 85d93c5c

- **Component:** `databricks-io`  |  **Category:** Spec/code drift
- **Evidence:** docs/specs/databricks-io/low-level.md:7 (`cache path management, streaming fetch-and-cache, cached-table read-back, in-memory fetch-progress tracking`) vs src/haute/_databricks_io.py:142 `class DatabricksSnapshotBuilder` — the only public surface the 258-line module actually has.
- **What is wrong:** The 0.7.0 refactor shipped on 24-Jul-2026 but only the Approved-change-contract sections of the specs were touched. Every ordinary present-tense section of both documents — Purpose, Behaviour, Interactions, Failure model, Module map, Key types, Control flow, Edge cases, Error handling, Testing — still describes the pre-refactor module: a table-name-keyed Parquet cache under `CACHE_DIR`, `fetch_and_cache`/`read_cached_table`/`cache_info`/`clear_cache`, module-global `_fetch_progress`/`_fetch_lock` (the module does not even import `threading`), and HTTP routes `POST /api/databricks/fetch`, `/fetch-progress`, `/cache-status`, `DELETE /cache`. None exist. Conversely the shipped surface — `DatabricksSnapshotBuilder` implementing the `SourceCacheBuilder` protocol, the `_iter_databricks_batches` generator, `_FROM_SQL_RE`, and dispatch from `src/haute/_input_providers.py:167-170` — is documented nowhere outside the temporary contract section. An engineer trusting this spec would code against `haute._databricks_io.read_cached_table` and `/api/databricks/fetch` and only discover at import/404 time that neither exists; a reviewer would approve a change on the basis of invariants (single-writer temp file, `Path.replace` atomicity, progress-slot races) that no longer describe anything in the tree.
- **Fix:** Rewrite every present-tense section of both files against the code as it stands today: module map responsibility for `src/haute/_databricks_io.py` = credential resolution, table/query validation, canonicalisation, and a bounded Arrow-batch `SourceCacheBuilder`; Key types = `DatabricksSnapshotBuilder`, `DatabricksConfigError`, `FetchIntegrityError`; Control flow = `_input_providers._snapshot_builder` -> `DatabricksSnapshotBuilder.build` -> `_iter_databricks_batches` -> `SourceCacheStore._write_output`; Failure model = the `/api/input-cache/*` job lifecycle, not the deleted `/api/databricks` fetch routes. Then delete the Approved change contract sections (see databricks-io-4).

#### `testing-credibility-1` — The entire databricks-io Testing section describes a test suite and a route surface that no longer exist

- **Component:** `databricks-io`  |  **Category:** Spec/code drift
- **Evidence:** docs/specs/databricks-io/low-level.md:258 names `tests/test_databricks_cache.py`, which does not exist; the bullets at :265-303 describe `fetch_and_cache`/`_cache_path_for`/cache-status/fetch-progress/`/fetch`, none of which exist in src/haute/_databricks_io.py (defs at :40,:66,:70,:78,:123,:142,:176,:236) or src/haute/routes/databricks.py (routes at :50,:74,:90,:108). Actual suites: tests/test_databricks_io.py (12 tests) and tests/test_databricks_endpoints.py:1 "Tests for retained Databricks browsing endpoints" (3 tests).
- **What is wrong:** The spec's per-file bullets claim coverage that provably does not exist and, in several cases, cannot exist because the production symbols are gone. Claimed for `test_databricks_io.py` (spec lines 265-283): `fetch_and_cache` happy path, progress set-then-cleared, no temp file leaked on error, `_cache_path_for` path-traversal, corrupt/truncated/zero-byte cached parquet, barrier-synchronised concurrent same-table fetch, `_validate_select_clause` "exhaustively for every keyword in `_DANGEROUS_SQL_RE`". None of `fetch_and_cache`, `_cache_path_for`, `cached_path`, `cache_info`, `clear_cache`, `fetch_progress`, or `read_cached_table` appear anywhere in src/haute/_databricks_io.py (its only module-level defs are `_validate_select_clause`, `_get_credentials`, `_canonical_table`, `DatabricksSnapshotBuilder`, `_iter_databricks_batches`, `_assert_no_rows_lost_after_retry`). The actual `_validate_select_clause` coverage is one 4-case parametrize at tests/test_databricks_io.py:41-46, not an exhaustive keyword sweep. Claimed for `test_databricks_endpoints.py` (spec lines 288-303): "fetch endpoint success, missing-connector `400`, timeout `504`", "cache status/delete round-trips; fetch-progress active/inactive", "table-name validation rejecting two-part and four-part names on route params" — none of those routes exist any more. The adjacent `> NOTE:` at docs/specs/databricks-io/low-level.md:250-255 compounds this by claiming an empirically-confirmed `500` from `/fetch`. This is the highest-risk drift in the corpus: it is a security-adjacent (SQL-injection validation, path-traversal, cache-file integrity) component whose spec tells a reviewer that a large defensive test suite is standing guard when 13 shallow unit tests are all that remain.
- **Fix:** Rewrite the databricks-io Testing section from the files as they are now: enumerate the 13 tests in tests/test_databricks_io.py and the 3 in tests/test_databricks_endpoints.py, delete the `test_databricks_cache.py` bullet, and delete every claim about `fetch_and_cache`/`_cache_path_for`/cache-status/fetch-progress/`/fetch` routes. Then record the resulting real coverage gaps (no path-traversal test, no cached-parquet corruption test, no concurrency test) as an explicit `Known coverage gaps` list, and fix the stale `> NOTE:` at :250-255 that asserts a `/fetch` route behaviour.

#### `frontend-graph-canvas-1` — WebSocket graph_update discards incoming `submodels`, then marks the graph saved — next save overwrites the file

- **Component:** `frontend-graph-canvas`  |  **Category:** Bug
- **Evidence:** frontend/src/hooks/useWebSocketSync.ts:261-267 (incoming frame destructured without `submodels`) and :317-328 (setNodesRaw/setEdgesRaw/setPreamble then `useGraphStore.getState().markSaved()`); the write-back is frontend/src/hooks/usePipelineAPI.ts:901 `const saveSubmodels = structuredClone(submodelsRef.current)`
- **What is wrong:** An external `.py` edit that adds, renames, or removes a submodel is broadcast with its new `submodels` map. The hook replaces three of the four store-owned graph fields and ignores the fourth, then calls `markSaved()`, so the user sees a clean, up-to-date-looking canvas while the store still holds pre-edit submodel metadata. Because `submodels` is also excluded from the dirty fingerprint (see frontend-graph-canvas-5), nothing flags the divergence. The next `handleSave` posts the stale `submodelsRef.current` back to the backend, silently reverting the externally-authored submodel state on disk. Meanwhile `validateConfigRefs`, `edgeInputName`'s submodel resolution and drill-in all read the stale map. No test covers this: neither frontend/src/__tests__/hooks/useWebSocketSync.test.ts nor the three frontend/src/hooks/__tests__/useWebSocketSync.*.test.ts files assert anything about incoming submodel metadata.
- **Fix:** Apply `g.submodels` through `setSubmodelsRaw` (and update `submodelsRef`) inside the same guarded block as nodes/edges/preamble, include it in the rollback path, and only then call `markSaved()`. If the frame legitimately omits `submodels`, fail loudly rather than silently retaining the previous map. Add a `useWebSocketSync` regression asserting an incoming submodel change reaches the store and survives a subsequent save.

### High (67)

#### `assistant-1` — Client disconnect between tool_started and the result append persists an orphaned tool call, breaking the session

- **Component:** `assistant`  |  **Category:** Bug
- **Evidence:** src/haute/assistant/_loop.py:331 `round_calls.append(event)` vs :352 `round_results.append(...)` — yields at :333/:341/:351 sit between them; the `finally` at :415-417 commits whatever is there
- **What is wrong:** The tool call is recorded in `round_calls` at line 331, but its result is only recorded at line 352 — after three `yield` suspension points. If the client disconnects (or the response is torn down) while the generator is parked at `yield AssistantToolStartedEvent`, `yield AssistantToolFinishedEvent`, or `yield AssistantGraphUpdatedEvent`, `GeneratorExit`/`CancelledError` arrives at that yield, skips line 352, and the `finally` at :415-417 commits and write-through-persists a turn containing an assistant message with `tool_calls` and no matching tool result. `_execute_shielded` only protects cancellation *during* tool execution, not at these yields. Every subsequent turn on that session re-sends the orphan through `store.history_window` (:285), and both `_anthropic_messages` and `_openai_messages` render it as a `tool_use`/`tool_calls` block with no following result — a conversation both providers reject — so the session fails permanently with `AssistantProviderError` until the orphan ages out of the 40-message window. The code even documents the hazard at :321-324 for the limit path, but leaves the far more likely disconnect path unguarded.
