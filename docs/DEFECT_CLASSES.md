# Defect Classes — the patterns that recur here

Individual bugs get fixed and forgotten. Some bugs are instances of a *shape* that recurs at every surface sharing a root cause, and fixing only the instance leaves every sibling live.

This page is the register of defect classes this codebase has identified and generalised. A class earns an entry when one concrete defect was recognised as an instance of a wider pattern, and the pattern was then named, hunted, or foreclosed. Every entry carries a **check recipe** — how to look for new instances.

It is a working tool, not a history. Use it two ways: when you fix something, ask whether it is an instance of a class here (and whether its siblings are live); when you build something new, run the relevant check recipes against it.

**A note on names.** Earlier internal notes referred to this register and its companion ledgers by code-names — the Maginot Line, DYLE, LOCARNO. That naming is retired here; the classes, the ladder, and the handling rules all live on this page.

## How a class gets handled

1. **When you catch an issue of an obviously generalisable class** — the same root shape plausibly exists at sibling surfaces — attempt to generalise: name the shape, hunt siblings proportionately (a grep, or a wider audit for broad surfaces), and fix or report what you find.
2. **When an issue is generalised**, record the class here — a new section, or a new instance under an existing one.
3. **New instances of known classes** are recorded wherever bugs are tracked, linked back to the class section here.
4. **Formalisation is the preferred follow-up** to any class entry: turn the class into tests at its vulnerability points, or harden the exposed code, and move it up the ladder below.

## The fortification ladder

Where a class sits, strongest first. The point of naming the rung is that "we know about it" is the *weakest* possible defence, and saying so out loud is what makes the next rung worth building.

- **① Impossible** — a guard, type, or chokepoint forecloses the class. A new violation cannot be written.
- **② CI-caught** — a test battery, source scan, or lint rule fails the build.
- **③ Sweep-caught** — a periodic review finds instances, but nothing blocks them.
- **④ Known** — a register entry only. No mechanism.

A fix that lands as corrected call sites leaves the class at ④. A fix that lands as architecture can reach ①.

## Established classes

### Mapping equivalence — name-to-artefact maps must respect the artefact's identity relation

**Shape.** Haute maps user-controlled names onto artefacts: node labels onto config files and generated functions, table labels onto cache files, data paths onto cache keys, table references onto remote tables. Every such map must respect the *artefact side's* identity relation, not string equality on the name side. Two labels differing only in case are one file on a case-insensitive filesystem; comparing them as strings lets one silently clobber the other.

**Why it keeps biting.** The platform relation is invisible on a developer machine where it happens to match. Every instance found so far passed all tests on the leg where the relation does not hold.

**Ladder: ①/②** — casefolded collision and stale-cleanup guards on the save path, shared canonicalisers, a sanitizer parity gate that fails both language suites on divergence, and a characterisation battery running on the non-Linux CI legs.

**Check recipe.** For any new surface deriving an artefact name or key from user input, run the standing checklist under standard 28 in [Commit Standards](COMMIT_STANDARDS.md). Sweep for new dictionary keys built from stringified paths, and for local regex sanitizers not routed through the **blessed sanitizers** — the identifier sanitizer, `_sanitize_func_name` in `src/haute/_graph_utils.py`, whose frontend counterpart is pinned to it by a fixture generated from the backend (`frontend/src/utils/__tests__/sanitizeParity.fixture.json`, regenerated by `scripts/regen_sanitize_parity_fixture.py`); and the filesystem-label pair, `sanitise_label_for_filesystem` in `src/haute/_api_input_schema.py` mirrored by `sanitiseLabelForFilesystem` in `frontend/src/utils/apiInputPorts.ts`.

### Platform divergence — code that behaves differently across platform stacks

**Shape.** Behaviour that varies with the platform stack is invisible on the development machine and bites on the other leg. Overlaps mapping equivalence where the divergence *is* an identity relation; kept separate because the fix posture differs — chokepoint modules, lint, and CI legs, rather than identity-relation guards.

**Ladder: ②** — encoding and path lint rules enforced repository-wide, line-ending pins, source scans forcing subprocess use through chokepoint modules, and Windows/macOS CI legs.

**Instances and detail:** [Platform Divergence](PLATFORM_DIVERGENCE.md).

**Check recipe.** New subprocess, `open`, or path call sites must pass the existing hygiene scans. Ask the catalogue's review-checklist questions of any I/O-adjacent change.

### Runtime path anchoring — relative paths resolved against the working directory

**Shape.** Every loader accepting a user-relative path must agree on what that path is relative *to* — and the process working directory is the accidental default. One node type mis-resolved a relative data path against the server's working directory; two sibling loaders had the same bug.

**Ladder: ①-partial / ④** — a shared resolution helper, `_resolve_runtime_data_path` in `src/haute/_builders.py`, exists and is the chokepoint, but nothing *forces* a new loader through it.

**Check recipe.** Sweep for new path resolution of user-supplied relative paths outside that helper. Any new node type that reads files must resolve through it.

### Write containment — code writing outside its owned roots

**Shape.** A write destination not derived from an owned, declared root. Four sub-shapes: repository pollution, user-home pollution, hardcoded system temp, and import-time path capture that defeats per-test redirection.

Notably, here the *detector was built first* and then enumerated the class empirically — a census across one test-suite run counted over 1,700 out-of-sandbox write events across 19 paths, the flagship being 139 tests appending to a log file in the user's real home directory because the path was frozen at import time.

**Ladder: ② for tests, ④ to ①-partial for product code** — see the test write sandbox section of the [engineering-quality specification](../specs/engineering-quality/low-level.md).

**Check recipe.** Run the backend suite with `HAUTE_TEST_WRITE_SANDBOX=observe` — the sandbox census: the terminal summary prints every out-of-sandbox write grouped by path class — and diff the escape list against the checked-in allowlist in the write-sandbox lint test. Grep for new home-directory, system-temp, or absolute-literal write destinations in product code.

### Fingerprint and cache-key completeness — keys that omit inputs affecting the cached output

**Shape.** A cache key that does not include everything the cached value depends on will serve a stale result with no invalidation and no diff. Complementary to mapping equivalence: that class governs key *identity* (two spellings, one artefact); this one governs key *completeness* (one key, two effective inputs).

Real instances here included a model cache keyed without the artefact's bytes, so a re-trained model served the stale one; and a UI staleness check hashing config but not the data source, so switching source presented the other source's result as current.

**Ladder: ④** — fixed per cache, with key-contract perturbation tests; no completeness battery.

**Check recipe.** For each cache or fingerprint, enumerate the inputs that affect the output and assert that each is either in the key or has a recorded exclusion decision. New caches state their key contract at the definition site.

### Two derivations of one contract — twins that must stay extensionally equal

**Shape.** Where the same rule is implemented on both sides of the wire — validators, mirrors, codecs, duplicated defaults — the two derivations drift. They can also be *in agreement and both wrong*, which no consistency check catches.

**Rule.** New cross-runtime rules come from one generated contract or one owning runtime — handwritten semantic twins are not written (Commit Standards, standard 1). A twin that already exists either calls a shared implementation, or carries a parity fixture or drift tripwire until it is retired. There is no third option that survives contact with time.

**Ladder: ① by standard for new code; ②-partial for legacy twins** — the proven idioms for the legacy set are a checked-in parity fixture with a regenerator that fails both suites on divergence (the sanitizer parity gate named under Mapping equivalence is the instance), and an interface-drift tripwire.

**Check recipe.** New frontend logic mirroring backend behaviour, or vice versa, must name its twin and its pin. Sweep for unpinned mirrors at review time.

### Sanitizer proliferation — name derivations bypassing the blessed sanitizers

**Shape.** Any site deriving a persisted name, key, or filename from a user string by local string-mashing — rather than routing through a blessed sanitizer (the two pairs named under Mapping equivalence) — is its own tiny identity relation, usually coarser than the blessed one. That makes it both a latent *collision* site (two labels converging on one artefact) and a latent *drift* site (its rules diverge as the blessed rules evolve).

The motivating instance minted its own filename by lowercasing and replacing spaces; two legally coexisting nodes derived one output file and the second save destroyed the first.

**Ladder: ①** at the class face — the birth-scan in `tests/test_repository_hygiene.py`, which runs in every backend lane, rejects new name-mint shapes outside the blessed modules at CI.

**Check recipe.** Sweep both source trees for filename, key, or identifier derivations from user strings via local case-folding, replacement, or regex that reach persistence or lookup without importing a blessed sanitizer. The birth-scan catches new sites at CI; this sweep is for legacy sites that predate the scan and for surfaces its pattern does not reach.

### Intent-signalling architecture — encode the intent, don't rely on discipline

**Shape.** This is a *meta*-class over fix forms rather than a defect shape. When a bug's root cause is a discipline that call sites must remember — don't call the solver inline, always pass the shared fingerprint, route writes through the chokepoint — the durable fix is restructuring so that violating the intent is harder, costlier, and more conspicuous than respecting it.

Three mechanisms, escalating:
- **M1 wrapper** — the invariant lives in a wrapper the caller cannot bypass.
- **M2 runtime guard** — context-sensitive entrypoints assert their execution context and fail loud, with a test pinning the guard so it cannot be dropped silently.
- **M3 chokepoint and privacy** — the dangerous callable is private to its one legitimate caller; the public surface exposes only the safe form.

**Check recipe.** Ask of every class-closing fix: *did this land as discipline or as architecture — and if discipline, what stops the next regression?* A fix that lands as corrected call sites only should say so, and say why. Any remembered-discipline rule that appears twice in the bug record is a candidate for restructuring.

### Low-context error surfaces — errors must inform without system context and carry an action

**Shape.** A user-facing error must be interpretable by a reader *without* the system's internal context — naming the user-model objects involved (node, column, objective, file) — and must say what to do next.

The motivating instance surfaced a training failure as a worker-wrapped library message that named no column, no task, and no fix, leaving the user unable to tell whether the platform or their data was at fault. A chokepoint that wraps remote exceptions verbatim launders library errors of their domain context.

This is the inverse twin of the sanitisation posture: sanitise-by-default strips detail that would *leak* (paths, secrets, raw stderr); this class demands detail that would *inform*. Both are properties of the same error-surface chokepoints and must be reconciled per surface.

**Ladder: ④ to ②-partial** — a curated-message field can cross the worker boundary un-wrapped, pinned by tests; nothing yet forces new failure paths to curate one.

**Check recipe.** Grep user-visible failure paths — worker wrappers, HTTP error details, frontend toast strings — for messages naming neither a user-model object nor an action. Any third-party exception crossing a route or UI boundary must be wrapped with both.

### Unpinned external behaviour — a dependency redefines a contract and the suite stays green

**Shape.** A dependency changes the *meaning* of something you rely on, and every test still passes because none of them asserted the behaviour independently. In the motivating instance a statistics library redefined a keyword argument from a raw exposure to a link-scale term; both versions fitted and converged, the full backend suite passed under both, and a model's intercept moved by more than a unit.

The defect is not the rename. It is that every existing test checked *shape* (keys present, types right), *liveness* (it succeeds, it returns 200), or *self-consistency* (the value equals what the dependency returned) — so all of them were satisfied by whatever the dependency now did.

**Rule.** Any behaviour relied on to calculate or report correctly — including from code you own — must be pinned by an assertion against a fixture derived *independently* of the code producing that behaviour. Ownership grants no exemption. A floor pin plus a lockfile is the aggravating condition: it makes the effective version a side effect of whoever last refreshed the lock, and nothing announces the change.

**Ladder: ②-partial** — a repository-wide sweep pinned the reliances it found: golden vectors for the random-number streams behind splits and folds, for the seeded hyperparameter-search sequence, and for the dataframe dtype spellings persisted in caches and configs; contract tests asked of the real libraries rather than fakes (CSV inference defaults, unpickler allowlist entries, model-registry keywords); and model-runtime packages pinned in the deployment image, with an artefact written by another version refusing to load rather than scoring wrong. Nothing yet forces a *new* reliance to arrive with its pin — that remains the check recipe's job at review time.

**Check recipe.** For every dependency relied on to calculate or report, enumerate the behaviours relied on — argument semantics, units and scale of returned fields, ordering, determinism under seed, error contracts — and ask of each whether a test asserts it against an expectation derived *without* that dependency. Grep the suites for shape-only assertions and for golden files generated by running the dependency; both pass vacuously through a semantics change. Treat any floor pin as unpinned behaviour until a fixture exists.

### Environment-default drift — pin the behaviour, not the platform

**Shape.** A platform flips a default under a tool, and the failure appears in one environment only. The motivating instance: a Node release shipped experimental web-storage globals default-on, whose stub landed on the global object before the test DOM environment initialised and silently shadowed the real implementation. CI stayed green because its Node version was pinned; local machines float ahead by design.

**Rule.** The durable defence is *not* enforcing a platform version everywhere — that re-breaks on the next upgrade, and some platforms offer no "behave like version X" switch at all, making version-pinning the only platform-level lever and the wrong one. Two-part posture instead:

- **(a)** Pin each drifting behaviour explicitly, with its own flag or config knob at the tool-config layer, and let the platform version float.
- **(b)** Add a cheap canary assertion naming the invariant, so the next silent drift fails loudly in one self-explaining place instead of producing dozens of baffling failures.

The class covers both directions: local-red/CI-green (a platform default flipped locally first) and local-green/CI-red (stale incremental build or type-check caches diverging from CI's clean environment — same shape, different tools).

**Ladder: ②** for the pinned instance — a provenance-checked canary with its own tests, plus a meta-test pinning that the pin itself stays present. The cache-side siblings remain ④, discipline only.

**Check recipe.** For any locally-only failure, or local-green/CI-red divergence: before debugging test logic, ask which platform default, experimental flag, or stale cache differs between the two environments. On a platform major upgrade, scan release notes for default-flipped experimental features that install globals visible to tests. Every behaviour pin carries a canary naming its invariant, and every canary points at its pin — so neither can be removed silently.

**Worked example:** [CI Mirror](CI_MIRROR.md) § Environment drift.

### Default drift — UI defaults standing in for backend contracts

**Shape.** A value the user never set resolves to a library or UI default at some layer, and the system proceeds as though the user had chosen it. The type specimen: an unset model loss and family silently resolving to a specific algorithm and metric set regardless of the family actually implied.

**Rule.** An unset required input fails loud at the boundary that needs it. A default is a product decision that gets documented; a default that exists only because some layer had to return something is a bug.

**Ladder: ④**.

**Check recipe.** Look for configuration that reaches a library default without an explicit decision. Any surface where the UI supplies a value the backend also defaults is a candidate — the two will diverge.

### Policy-by-convention with no ratchet — most of the tree follows a rule, one entrant does not

**Shape.** A rule is stated in prose and followed by nearly every entry, so the uniformity itself starts to read as enforcement and nobody checks. Then one entrant does something different and no mechanism rejects it. The type specimen: dependency pinning doctrine requires a floor *and* a cap on every published dependency; two provider SDKs entered with a floor and no cap, days after the rule had been given CI lanes, and sat there among twenty-two compliant neighbours until an audit read the file.

**Why it keeps biting.** The aggravating condition is a second layer that resolves the same information. Every check ran against the *lockfile*, which pins exact versions and hashes, so nothing ever re-read the declaration the rule actually governs — and the declaration drifted unobserved. Wherever a lockfile, cache, snapshot, or generated artefact sits between a declaration and the gates, assume the declaration is unguarded until shown otherwise. A related symptom appears first in documentation: when the same rule is restated in more than one place, the statements diverge before the code does.

**The sharper form.** The founding cases were dependencies the manifest named but under-constrained. The harder version is a dependency it does not name at all. A library arriving transitively through two others, neither of which bounds it, is not under-governed — it is outside the policy's jurisdiction entirely, and a declaration-layer check cannot see it by construction, because there is no declaration to read. One was found this way: a transitive data library whose new major crashed the process on a path reachable from a live server request, while the lockfile still pinned a working version and a fresh install did not. Bounding such a dependency means declaring one the project does not otherwise need, purely to constrain a transitive — a policy decision, not a lint fix.

**Rule.** For any policy the tree follows by habit, the question is not "is it written down" but "what rejects the next entrant" — and specifically, does any check read the artefact the policy governs. Ask what the policy's jurisdiction is before asking whether it is enforced.

**Ladder: ② for declarations, ④ for resolved artefacts, ④ for undeclared transitives** — a lint reads both dependency manifests and fails the build on a published dependency missing a floor or a cap, an exact-pinned published dependency, a non-exact tooling pin, or a registry-bypassing runner invocation on an executable surface; a live-tree test makes it a standing ratchet. Nothing yet reads the *lockfile* against the declaration — whether a resolved version sits at the very top of its declared band, or whether the lock contains a release since yanked from the index. Nothing constrains an undeclared transitive at all; the one found above surfaced only from a scheduled lane that resolves dependencies fresh, and only after that lane was repaired from an unrelated long-standing failure — a defence everyone assumed was present while it was silently absent.

**A second lesson from the same case.** The scheduled fresh-resolve lane existed and was assumed to cover these dependencies, but the fast test subset it runs imported neither of them — so the lane resolved them and never touched them. A verification lane covers what its tests actually import, not what it installs. Adding one file to that subset closed it. Ask of any early-warning lane which of its declared subjects its tests genuinely exercise.

**Check recipe.** Grep for rules that live only in prose, then count compliant entries: a policy at N−1 of N compliance with no failing check is an instance. Ask what artefact the rule governs and whether any check opens that file. Treat divergence between two statements of the same rule as the first symptom.
